# 三维数据提资（新入口）· 元素与契约字段对照

与 `MODEL-UPDATE-FIELD-MAP.md`、`QUEUE-FIELD-MAP.md` 同一套做法与同一条硬规矩：**这张表是实现的验收基准，
界面上每一个数字、每一条状态文案都必须在这里找到出处；找不到出处的东西不许画上去，也不许实现出来。**

来源三类：

| 记号 | 含义 |
|---|---|
| **契约** | gen-model 或 rs-server 现有接口已经给得出来的字段 |
| **本地** | plant-ui 自己能算的量（计数、计时、队列快照里的下标、表单状态） |
| **待新增** | 要 gen-model 补字段才有，注明是计划阶段四的哪一条（G1 – G5），以及在那之前画什么。五条的规格草稿：`docs/plans/2026-11-26-gen-model-spec-draft-submission-priority-update.md`（字段名以那边定稿为准） |

决策见 `docs/adr/0036-data-handover-is-gated-by-a-precheck-of-the-elements-libraries.md`，计划见
`docs/plans/2026-11-26-data-publish-precheck-plannotator.md`。画板在 `design/三维数据提资.pen`：**S15** 需要更新、
**S15-A** 更新中、**S15-B** 已是最新（放行那一刻）、**S15-C** 形态表（整体判决 7 种、库行 13 种）。

接口：

- **检查** `GET /api/v1/node/model-status?refno=`（gen-model 接口文档 §4.5.3），每个提资元素一次，只读。下文简称「节点状态」。
- **更新** `POST /api/v1/update/execute`（`dbnums` 子集），两次：先落后的库，回执到了再发需初始化的库。
- **队列** `GET /queue`、`/tasks`、`/dbnums`、`/health`（常驻轮询，与任务队列面板同一份）。
- **预览 / 查待删除 / 提交** rs-server，与旧入口「三维数据接口」相同，不在本表展开。

界面上不出现会话号与契约字段名；时刻一律是 E3D 写入时刻，格式 `MM-DD HH:MM`（ADR-0019）。

## 3. 整体判决（S15-C 左栏）

判决只看库行形态归成的五类（不挡提交 / 等人点 / 在排或在跑 / 更新不了 / 没查成），判据在 `data_publish_check::judge`。

| 判决 | 何时 | 主操作 | 「提交」 |
|---|---|---|---|
| 正在检查 | 问了还没回，手上没有可画的结果 | 无 | 灰 |
| 要提资的数据已是最新 | 每一行都不挡提交 | 提交 | 可用；点下去先再查一次 |
| 要提资的数据不是最新 | 至少一行「落后」或「需初始化」，没有更新不了的、没查成的 | 更新到最新 · N 个库（N = 这两类行数） | 灰 |
| 正在把要提资的数据更新到最新 | 有行在排、在跑或模型追赶中，没有等人点的 | 更新中…（灰） | 灰 |
| 有库更新不了 | 至少一行更新不了，或有元素在文件最新保存里已经没有 | 移出这 N 个元素 | 灰 |
| 没查成 | 有元素没查成，或有行判不出 | 重新检查 | 灰 |
| 这台模型服务不支持提资前检查 | 没有节点状态这条路由，或这一形态不入库 | 提交 | 可用，不拦 |

「不支持」的两个来源：节点状态回裸 404 / 405（`route_missing`，老服务端）；`/health.data_face = read-through`，或节点状态的
`data_ingest.libraries[].verdict = not_applicable`（这一形态不入库）。「没查成」是别的任何失败（连不上、超时、内部错）。
「文件里已经没有」是带包封的 404 `REFNO_NOT_FOUND`。三者按错误码分，不解析 message。

横幅说明里的计数（「1 个库的数据水位落后于文件，1 个库尚未初始化」等）都是本地对库行的计数。

## 4. 库行（S15-C 右栏）

一行是提资元素所在的一个库。列：设计库 | 文件最新保存 | 数据水位 | 状态；第二行左边是「N 个提资元素 · 怎么回事」，右边是「接下来该做什么」。

| 元素 | 示例 | 来源 | 出处 |
|---|---|---|---|
| 库号 | `db8000` | 契约 | 节点状态的 `dbnum` |
| 库类型 | `DESI` | 契约 | `/dbnums` 那一行的 `db_type`；取不到就不画。库文件名（`file_name`）挂在悬停上 |
| 文件最新保存 | `11-26 10:42` | 契约 | 节点状态的 `library.file_latest_time`。读不出就留 `—`，不回落成序号 |
| 数据水位（已追平） | `11-26 10:42` | 契约 | `library.applied_sesno == file_latest_sesno` 时，数据水位就停在文件最新那一次保存上，用同一个时刻 |
| 数据水位（还没建立） | `尚无数据水位` | 契约 | `library.initialized = false` |
| 数据水位（落后时） | 画板 `11-25 17:30`；**今天画 `—`** | **待新增 G4** | 要 `library` 加数据水位那次保存的时刻（本端已按 `applied_sesno_time` 解，给了就画）。给之前停在哪一次保存说不出，留空，不拿别的时刻顶 |
| 状态：已是最新 | | 契约 | 数据水位追平 ∧ 队列里没有它的活 ∧ 库级判决不是 `lagging`、没有模型任务在跑 ∧ 每个提资元素的 `verdict` 是 `latest` 或 `empty` |
| 状态：提资范围已追平 | + `整批单元 9 / 21 个 · 后台继续` | **待新增 G3** | 要服务端按根回答「追平没有」。本端按暂定的 `publish_ready` 解（字段名随 gen-model 规格定稿）；给之前这一形态不出现，要等这个库的任务跑完 |
| 状态：落后 N 次保存 | `落后 3 次保存` | 契约 | `library.file_latest_sesno - applied_sesno`（只当计数说，不露会话号） |
| 状态：需初始化 | | 契约 | `library.initialized = false`，且没有别的理由让它更新不了 |
| 状态：模型追赶中 | 画板 `模型追赶中 · 12 根`；**今天不带根数** | 契约 | 数据水位追平，而 `library.model_verdict = lagging`、`library.model_task_running`、或有元素的 `verdict = updating`。根数节点状态不给，不画 |
| 状态：增量更新 / 首次导入 · 排队中 | `队列第 1 位 · 已排 00:18` | 契约 + 本地 | 队列快照里这个库有 `queued` 行（位置是快照下标，已排时长从 `created_at` 算）。首次导入还是增量看 `library.initialized`。回执刚到、快照还没跟上时写 `已排上` |
| 状态：增量更新 · 应用中 / 模型重算中；首次导入 · 运行中 | `已用 01:12` | 契约 + 本地 | 队列快照里这个库有 `running` 行。「应用中」与「模型重算中」的分界与任务队列面板同一条（`total_units` 出现）；已用时长从 `started_at` 算 |
| 画板上的「优先增量更新」「已提到队首」 | **今天写「增量更新」，按入队序排** | **待新增 G1** | 执行请求收「优先根」并把这些库的批次提到队首之后才成立 |
| 状态：已阻断 · 文件回退 / 路径迁移 / 类型变化 / 同号重复 / 文件缺失 | | 契约 | `/dbnums` 那一行的 `blocked` 与 `anomaly`；详情是与模型更新窗同一段阻断文案。**文件回退即使没标 `blocked` 也归这里**（ADR-0036 D5） |
| 状态：够不着 | 灰 | 契约 | `/dbnums` 那一行的 `not_in_project`。当前项目目录里没有它的文件，「文件最新保存」「数据水位」两格都留 `—` |
| 状态：不在本期执行范围 | | 契约 | `/dbnums` 的 `excluded`，或节点状态的 `library.in_watch_scope = false`，或 `data_ingest` 的原因码 `out_of_scope` / `scope_unresolved` |
| 状态：上次更新失败 | `连续失败已停，这里不替它重试：…` | 契约 | `data_ingest.libraries[].last_failure.parked`（原因取 `last_failure.reason`），或原因码 `parked_after_failures` |
| 状态：已是最新却缺行 | | 契约 | 数据水位追平而 `data_ingest` 说这个节点缺行（原因码 `up_to_date_rows_missing`，或 `verdict = missing`） |
| 状态：此刻排不了 | 服务端的原话 | 契约 | `data_ingest.libraries[].action = not_enqueued` 且带其余原因码（房间参照模型没就绪、增量消费关着……），详情照登 `message` |
| 状态：模型没追平 | | 契约 | 数据水位追平、没有任务在跑，而有元素的 `verdict` 是 `lagging` / `partial` / `not_generated` |
| 状态：没查成 | | 契约 | 有元素的 `verdict = unknown`（原因取 `verdict_reason`）。整个请求失败的元素不知道属于哪个库，不进行表，列在表下的提示条里 |

更新不了的行，「数据水位」那一格不用提醒色（催也没用，状态列已经说了为什么）；行按「更新不了 → 没查成 → 等人点 → 在排或在跑 → 不挡提交」排，同类按库号。

判据顺序写死在 `data_publish_check::judge_lib`：范围 → 阻断 → 已停自动重跑 → 按单元放行 → 队列里已有它的活 → 服务端说排不了 →
需初始化 → 落后 → 已是最新却缺行 → 节点判不出 → 模型追赶中 / 没追平 → 不挡提交。

## 6. 底部操作

| 元素 | 来源 | 出处 |
|---|---|---|
| 提示句 | 本地 | 按整体判决出（§3）；「更新到最新」点不了时换成点不了的理由；最近一次提交 / 更新的结果压在最上面，直到提资元素有增删或再次操作 |
| 「更新到最新」点不了的理由 | 契约 | 身份没对上（`task_queue::Vm::can_mutate`）、服务不消化执行请求（`execution_blocked_reason`，来自 `/health`）、队列已暂停（快照的 `paused`） |
| 「提交」灰着的理由 | 本地 | 悬停给：没有元素 / 正在检查 / 不是最新 / 正在更新 / 有库更新不了 / 没查成 / 正在提交 |
| 提交结果 | 契约 | rs-server 回的那一句（与旧入口进日志的是同一句），这里另写在窗口底部 |

## 7. 演示模式（`PLANT_UI_SIM=1`）

剧本树上的节点各挂在一个剧本库上（`sim.rs::sim_check_dbnum`），凑齐四种行：

| 节点 | 库 | 行形态 |
|---|---|---|
| `/SIM-SITE-A`、`/SIM-Z1`、`/SIM-PIPE-101`、`/SIM-PIPE-101/B1`、`/SIM-EQ-201` | db7001 | 落后 2 次保存 |
| `/SIM-Z2` | db7002 | 落后 1 次保存 |
| `/SIM-PANEL-7` | db7003 | 已是最新 |
| `/SIM-EQ-305` | db7006 | 需初始化（首次导入时有「解析保存」进度） |
| `/SIM-SITE-B` | db7004 | 已阻断 · 文件回退 |
| 其余 | — | 文件最新保存里已经没有这个元素 |

剧本里第一轮房间收敛之后 db7001 / db7002 会各再存一次盘（一次性）：这时候这扇窗若停在「已是最新」，几秒内自己变回「不是最新」
（`/dbnums` 上水位动了 → 重新检查）；手快赶在它前头点「提交」，也会被提交前那次检查拦下。正好看得到硬拦。
整条路的目检记录：`docs/evidence/2026-11-26-data-handover-sim-inspection.md`。

## 8. 画廊场景（`rs-plant --gallery=s15…`）

不接后端、不起三维、不用点，把这扇窗的某个形态直接摆出来对画板：`s15`（需要更新）、`s15-a`（更新中）、`s15-import`（首次导入在跑）、
`s15-b`（已是最新）、`s15-stuck`（有库更新不了）、`s15-unknown`（没查成）、`s15-unsupported`（不支持检查）、`s15-empty`（还没有元素）、
`s15-bar`（收成一条）；场景名后缀 `@dark` 换深色主题。各场景摆的事实在 `crates/plant-ui-app/src/gallery_handover.rs`，
与本表用的是同一套契约字段；这里的答复是编的，不能当成服务端的行为依据。
