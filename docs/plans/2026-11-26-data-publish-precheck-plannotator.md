### 为什么会交出旧数据

- 提资整条路不读水位、不问模型服务：`data_publish.rs` 与 `data_publish_api.rs` 里没有一处看数据新不新。
- 服务供数下模型树读的是文件，rs-server 读的是库。所以能选到库里还没有的元素（库没初始化），也能选到库里是旧版本的元素（数据水位落后）。前者预览只回「该参考号下没有可发布的节点」，后者交出去的是旧数据，哪里都不报。

### 已经存在、本次直接复用的

- **`GET /api/v1/node/model-status?refno=`**（gen-model 接口文档 §4.5.3，ADR-099）：只读、按需算、不落库，文档记的实测是 19 – 41 ms。对任意节点一次回答：
  - 所属的库 `dbnum`；
  - 库的事实 `library`：`file_latest_sesno` / `file_latest_time`、`applied_sesno`、`initialized`、`model_verdict`、`data_batch_running`、`model_task_running`、`in_watch_scope`；
  - 节点自己的模型判定 `verdict`：`latest` / `lagging` / `partial` / `not_generated` / `updating` / `empty` / `unknown`；
  - `data_ingest` 一块：缺不缺入库数据、排不排得上、排不上的原因码、上次失败。

  本端今天只解了 `data_ingest`（`model_update_api::node_model_status_data_ingest`）。
- **`POST /api/v1/update/execute` 的 `dbnums` 子集**（ADR-020）：`model_update_api::execute` + `data::Req::ModelUpdateExecute { dbnums, from_wizard }`，库行「提前执行」（`Cmd::RunDbnumNow`）走的就是它。需初始化的库经它做首次导入，系统库先行。
- **队列读数**：`task_queue::Vm`（`paused()`、`active_tasks()`、任务行的 `units_done` / `total_units`）。轮询常驻（`main.rs` 的 `poll_queue`：有活 1 秒一拍，空闲 5 秒）。
- **`/dbnums` 行**（`task_queue::DbnumStatus`）：`blocked` / `anomaly` / `excluded` / `not_in_project`。
- **取回工作**：`main.rs` 的 `get_work_with_models_for_tasks`。
- **模拟引擎**：`sim.rs`（`PLANT_UI_SIM=1`），已有 `execute` / `poll` / 节点预检的剧本。

## 决策摘要

用户已定（2026-11-26）：

| 编号 | 决策 | 结论 |
|---|---|---|

| D3 | 需初始化的库什么时候起跑 | **点「更新到最新」时一并排上，排在增量更新后面**；检查只读，不排任何任务 |

| 编号 | 决策 | 结论与理由 |
|---|---|---|
| D4 | 检查问谁 | 逐个提资元素问 `node/model-status`，8 路并发。一条接口同时给出所属库、两个水位、文件最新保存时刻、节点模型判定和排不上的原因码，不用本端拼 `/dbnums` 与树上的库号 |

| D10 | 老服务端与读透形态 | `node/model-status` 没有这条路由，或 `data_ingest.verdict = not_applicable`：检查整块不画，只留一句话，提资照旧、不拦。判不了就不装作判过 |
| D11 | 代码落在哪 | 判据与行形态是纯函数，放新文件 `crates/plant-ui/src/data_publish_check.rs`；新窗放 `crates/plant-ui/src/data_handover.rs`；宿主侧的并发查询、两发执行与回包处置放 `crates/plant-ui-app/src/data_handover.rs`。`data_publish.rs` 只放宽 4 个函数的可见性 |
| D12 | 模型没追平又没有任务在跑 | 归「更新不了」，文案指向模型树右键「重新生成模型」。本期不在提资窗里替人重算 |

## 阶段三：更新到最新（今天的服务端）

### 目标

一个按钮把落后的库和需初始化的库都排上，落定后自动取回工作并重新检查，结论转绿后「提交」可用。

### 实现

- `main.rs` 处理 `Cmd::UpdateDataPublish`
  - 先过 `model_service_executable()`。
  - 按 D6 两发 `Req::ModelUpdateExecute`。`from_wizard: bool` 换成来源枚举（向导 / 队列面板 / 提资），回执据此路由；提资来的回执记下任务号。
  - 入队被拒（422 / 409 / 房间初始化门）：横幅下一行原因，日志留原文；行形态回到落后或需初始化。
- 进度：行形态每拍从 `task_queue::Vm` 读（排队第几位、在跑的阶段、`units_done / total_units`、`data_progress`）。
- 落定：记下的任务全部终态 → `get_work_with_models_for_tasks` → 取回工作回包之后重新检查。失败的任务行形态落到「上次更新失败」。
- 暂停（D7）：`queue.paused()` 时主按钮灰，给「打开任务队列」。
- 卡片文案按能力档出：按库档写「排入队列」「这个库的任务跑完才能提交」，不出现「提到队首」「提资单元先生成」。
- `sim.rs`：补「两发保序」与任务落定后节点事实翻新，模拟模式下能从 S15 走到提交。

### 验收

- 模拟模式：需要更新 → 点一次 → 更新中 → 可以提交 → 提交成功，全程不用离开提资窗。
- 隔离环境的真服务端（队列开着）：一个落后的库加一个未初始化的库，点一次按钮；队列里增量在前、首次导入在后；落定后自动取回工作、检查转绿、提交成功。
- 队列暂停：按钮灰、文案对、没有任何请求发出。
- 阻断的库：不在 execute 的名单里（抓请求体核对）。

## 阶段四：gen-model 契约（另仓，另起 spec）

| 编号 | 要什么 | 本端哪一格等它 | 没有时怎么画 |

| G1 | execute 收「优先根」（提资元素的参考号，服务端解成交付单元）：这些库的批次提到队首、不打断在跑的；模型段先算这些根；它们的房间归属随即重算 | 「提到队首」「提资单元 2 / 3」进度条 | 按库档：排入队列，一条「交付单元 14 / 24」 |

| G3 | 按根回答「追平没有」：模型已重新生成、房间归属已重算（`node/model-status` 加一格，或任务行报优先根的完成数） | 「提资范围已追平」与 D2 的放行 | 按库档：等这个库的任务跑完 |
| G4 | `library` 加数据水位那次保存的时刻 | 「数据水位」列的时刻 | 只写「落后 N 次保存」 |
| G5 | 队列暂停时放行提资带出的更新（规则同 Spec 041 对节点入库的放行） | 「自动同步已关闭 · 只放行这 2 个库」 | D7：按钮灰，请人先恢复出队 |

## 风险与已知限制

1. **检查与组包之间仍有窗口**。提交时复查之后、rs-server 组包之前又有新保存，交出去的仍可能旧一次。本端做不到原子；要关死得 rs-server 在回执里带上组包时的数据水位，不在本计划内。
2. **数据新不新按库判，不按元素判**。`node/model-status` 的「落后」只看几何变化，改名、改描述不算，而提资交的正是属性，所以数据这一侧只认库的数据水位。代价：同库别的元素有新保存时，没被改到的提资元素也要等一次增量。
3. **人工 execute 遇到文件回退会清库重建**（gen-model ADR-021）。名单里不放阻断与回退的库，但检查与点击之间文件回退了的话拦不住；模型更新向导有同样的窗口。
4. **元素很多时的往返**。200 个元素是 200 次请求，8 路并发按文档的单次用时估算约 1 秒，没有实测；首次问一个大节点没有缓存时会慢。超过 500 个时分批并画进度。
5. **房间归属在按库档下是间接保证的**：靠「这个库没有在排或在跑的任务」。房间泳道有待重算且读得到（`task_queue::Vm::rooms_pending`）时并入判据；读不到时不拦，面板上写明这一格没判。
6. **首次导入很重、不可取消**。Spec 041 的实测：7997 从请求到做完 142 秒，样例里最大的 7333 是 496 秒。卡片里写明。
7. **工作区有 4000 多行未提交改动**，与本计划动同一批文件。叠着做能做，但本计划的提交会与那批改动缠在同一个文件里。
8. **浏览器端没有单独验**。并发查询用的是现有的 `ehttp` 与并发道，按理两端一致；阶段六在浏览器里走一遍主流程，验不到的记进证据文档。
