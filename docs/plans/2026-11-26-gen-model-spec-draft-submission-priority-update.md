# Spec 046（草稿，编号以 gen-model 为准）：提资前把要提资的节点优先更新到最新，并按节点回答「可以提资了没有」

**Created**: 2026-11-26  
**Status**: Draft。在 plant-ui 仓起草，还没进 gen-model。「背景事实」是我只读 gen-model（`refactor` @ `ff85bcc99`）的文档与源码核对的，
「Assumptions」是没有追到底的推断；两节都要 gen-model 一侧纠正。批准后移到 `gen-model/specs/046-…/spec.md`，`plan.md` /
`tasks.md` 由那边另写。本稿不改 gen-model 的任何代码。  
**Input**（plant-ui 用户原话，2026-11-26）: 「分析当前 plant-ui 的三维数据接口，创建功能，我想加上需要提供一个检查，比如说最新的

**出处**: plant-ui `docs/adr/0036-…`（决策）、`docs/plans/2026-11-26-data-publish-precheck-plannotator.md`（计划，阶段四的 G1 – G5）、

## 目标

plant-ui 新加的入口「三维数据提资」在提交前检查提资元素所在的库，数据不是最新就不让提交，并给一枚「更新到最新」。今天这枚按钮
只能按库排队、等整库任务跑完才放行：提资 3 个支管，要等这个库被这几次保存波及的几十上百个单元全部重算完，前面还排着别的库。

做完之后要成立的五件事：

1. **按节点答得出「可以提资了没有」**：这个节点（连同全部后代）的数据行、模型行、房间边，在库里是不是都已是库文件最新那一版。
   答「是」的时候，直连库的读者（rs-server）此刻组包拿到的就是最新的。任务还在算这个库其余单元的时候也答得出。
2. **提资带出的更新先做提资要的那一部分**：数据应用之后，模型半边先算提资节点下的单元。
3. **排在前面**：不等队列里无关的库，不打断正在跑的那一批。
4. **队列暂停时也做得成**，而且不连带放行别的库（与 Spec 041 对节点入库的放行同一个道理）。
5. **数据水位停在哪一次保存，说得出时刻**。

读透形态不入库，整份不适用：plant-ui 在那一形态下不检查、不拦（ADR-0036 D7）。

## 背景事实（2026-11-26 只读核对，gen-model `refactor` @ `ff85bcc99`）

### 提资读的是哪一份数据

- rs-server 直连同一个 SurrealDB（RocksDB 后端），与 gen-model 共用表（`docs/2026-10-27-rs-server-storage-scheme-adaptation.md` §1）。
  gen-model 进程内的模型投影它看不见（ADR-076 D1）。所以「能不能提资」只能按**库里已经落盘的**算。
- 提资成功时 rs-server 写 `datacenter_version`，其中记着「提资时的会话号」（gen-model `CONTEXT.md`「提资版本记录」「提资基准」）。

### plant-ui 今天怎么判、怎么排（已实现，按库档）

- **检查**：逐个提资元素问 `GET /api/v1/node/model-status`（8 路并发），按 `dbnum` 归成行。数据新不新只认
  `library.applied_sesno` 与 `file_latest_sesno`；节点的 `verdict` 只用来回答模型追平没有（它只看几何变化，改名、改描述不算，
  而提资交的正是属性）。
- **放行判据**：库的数据水位追平文件 ∧ 这个库没有在排或在跑的任务 ∧ 每个提资元素的 `verdict` 是 `latest` 或 `empty`。
- **更新**：两发 `POST /api/v1/update/execute`（`dbnums` 子集），先落后的库、回执到了再发需初始化的库。发之前客户端自己把
  阻断、文件回退、已停自动重跑、够不着、不在范围的库剔掉——因为人工执行会清失败账、遇到回退会清库整库重建
  （gen-model `docs/specs/web-service-api.md` §4.3，下称接口文档），那不是「更新到最新」该替人做的事。
- **队列暂停时**按钮灰着，请人先去恢复出队。

### 与要求的差距

| 编号 | 要什么 | 今天 | plant-ui 哪一格在等 |

### 现状里要保留的

- 一条队列、一个派发器，不开第二条消费路径（ADR-011）；同库严格串行，正在跑的批次不打断、没有取消。
- 阶段屏障与独占（ADR-025）照旧：系统库、目录库先行，基线与重建独占。
- 模型水位仍是「到这一版每个生成单元都已落库」的承诺（ADR-060 / ADR-079），不加逐根的持久行。
- `POST /api/v1/update/execute` 的请求、回执、语义一字不动；`node/model-status` 现有字段与判据不动，只加不改。
- 老客户端不受影响；新客户端连老服务端退回按库档（plant-ui 已按「服务端给了才画」实现）。

## Assumptions（我做的假设，请纠正）

1. **数据水位到 T 之后，直连库读到的这个库的数据行就是 T 那一版**（ADR-021 的不变量），而且稳态增量窗口里这一步先于模型半边做完。
   所以任务还在算其余单元的时候，只要提资节点下的单元落了盘，这几个节点就可以答「是」，不必等任务收尾，也不必拆任务。
   请确认两点：（a）数据尾事务提交时，这一窗的属性行确实都已落盘——ADR-076 D4 说属性写走共用写入队列、收尾等队列排空，D10
   承认「新模型 + 旧属性」的中间态；尾事务在不在排空之后，我没有追到底。（b）一根记进账本时，它的模型行与房间边确实都已落盘，
   而不只是进了投影。两点任一不成立，FR-002 的判据要换成能证明「已落盘」的事实。
2. **一个节点的数据新不新按库答就够**：库的数据水位追平库文件最新 ⇒ 这个节点的数据行是最新的。不做按元素的数据差分。
3. **优先名单 = 提资节点子树里的生成单元**，与 `node/model-status.units` 是同一段枚举；节点在某个单元之内时就是那一个单元。
4. **本窗没波及的根可以当场答「已落定」**，不必等任务收尾盖模型水位——窗口规划器对它已经有结论（回执里的前移名单）；
   规划退化（放弃前移）时不算。
5. **首次导入的数据水位在任务收尾才盖**，所以首次导入天然没有提前放行，与用户定的一致，不用为它做任何事。
6. **rs-server 不改**。检查与组包之间的窗口（检查之后、组包之前又来一次保存）本规格不关。
7. **提资节点数量级**：一次几个到几十个，多半是 BRAN / EQUI / PIPE 这一级；也可能是 ZONE / SITE。

## User Scenarios & Testing

### User Story 1 - 按节点问「可以提资了没有」（Priority: P1）

设计人员把几个支管加进提资清单。界面问服务端：这几个节点此刻组包拿到的是不是最新的。服务端按节点回答是、不是（并说差在哪）、
或判不了。

**Why this priority**: plant-ui 的硬拦就靠这个答案。没有它，只能等整库任务跑完；有了它，其余几条才有意义。

**Independent Test**: 不动队列与执行，只对若干节点问（包括一批增量任务跑到一半的时候），逐个对照库里的行与库文件最新会话上的解析结果。

**Acceptance Scenarios**:

1. **Given** 库的数据水位等于库文件最新、没有任务在跑、节点下的生成单元都按这一版生成过、库不欠房间重算，**When** 问这个节点，
   **Then** 答「是」，并给出所依据的会话号。
2. **Given** 库文件比数据水位新，**When** 问，**Then** 答「不是」，原因是数据落后；不因为这个节点恰好没被改到就答「是」。
3. **Given** 这个库的增量任务正在跑、数据水位还没盖到文件最新，**When** 问，**Then** 答「不是」，原因是数据正在写，并带上那条任务号。
4. **Given** 任务还在跑、数据水位已盖到文件最新、节点下有单元还没按这一版落盘（排着、在算、或失败待重试），**When** 问，**Then** 答「不是」，
   说清是还在等还是失败，并给出「共几个单元、落定几个、还差几个、失败几个」。
5. **Given** 任务还在跑、数据水位已盖到文件最新、节点下的单元都已按这一版落盘，而这个库其余单元还在算，**When** 问，**Then** 答「是」。
6. **Given** 所在库欠整库房间重算，或房间参照模型没就绪，**When** 问，**Then** 答「不是」或「判不了」，原因是房间；不答「是」。
7. **Given** 库从没初始化过，或首次导入还在跑，**When** 问，**Then** 答「不是」，原因是还没有数据 / 数据正在写。
8. **Given** 服务进程重启过、账本是空的，**When** 问，**Then** 只凭持久事实作答（模型水位、持久行回读）；证明不了就答「不是」或「判不了」。
9. **Given** 读透形态，**When** 问，**Then** 答「不适用」，不算错误。

### User Story 2 - 「更新到最新」先做提资要的那一部分（Priority: P1）

检查说两个库落后、一个库没初始化。人点「更新到最新」。服务端把这几个库排上：落后的库应用并提交数据之后，模型半边先算提资节点下被波及的
单元，它们一落盘这几个节点就可以提资；任务接着算这个库其余被波及的单元。没初始化的库排在增量后面，整库首次导入，没有提前放行。

**Why this priority**: 这是用户原话里的「针对我们要发的数据进行优先增量更新」。只有第一条故事而没有它，「是」出现得早晚全凭运气
（看提资单元排在单元清单的哪里）。

**Independent Test**: 取一个落后若干次保存、被波及单元远多于提资单元的库，带 3 个提资节点发起，记下「这 3 个节点可以提资」与「这个库
整窗做完」两个时刻，前者应明显早于后者，并核对前者那一刻库里的行。

**Acceptance Scenarios**:

1. **Given** 库落后、本窗波及 24 个单元、其中 3 个在提资节点下，**When** 带这几个节点发起，**Then** 数据提交后模型半边先做这 3 个；
   它们落盘后第一条故事对这几个节点答「是」，这时任务还在做其余 21 个；全部做完才盖模型水位，与今天一样。
2. **Given** 提资节点下的单元本窗没被波及，**When** 发起，**Then** 数据提交、规划出来之后这几个节点即答「是」，不为它们重算任何单元。
3. **Given** 库没初始化，**When** 发起，**Then** 排整库首次导入（系统库先行），整库做完才答「是」。
4. **Given** 同一次发起里有落后的库也有没初始化的库，**When** 发起，**Then** 落后的库排在首次导入之前。
5. **Given** 这个库已有任务在跑，**When** 发起，**Then** 不打断它；回执指向那条任务。它的单元清单里还没做的提资单元能提前就提前，
   不能就照原次序，回执说明是哪一种；它的窗口没覆盖到文件最新时另排一行接在它后面（现有规则），那一行带优先名单。
6. **Given** 这个库数据已是最新、提资节点下有单元模型没追平（上次失败、或模型水位落后），**When** 发起，**Then** 只为这几个单元排一条补算，
   或把它们在已有补算里提前；不清失败账，已放弃的根不动。
7. **Given** 库被阻断、文件回退、已停自动重跑、不在执行范围，**When** 发起，**Then** 这个库一行不排，回执逐库说原因；别的库照排。
   文件回退不清库。
8. **Given** 任务做到一半库文件又来了新保存，**When** 问，**Then** 第一条故事答「不是」（数据落后），由调用方再发起一次。

### User Story 3 - 提资带出的行排在前面（Priority: P2）

队列里排着别的库的增量。人在提资窗口前等着。提资带出的那几行排到这些排队行前面，正在跑的那一批跑完就轮到它。

**Why this priority**: 没有它，前两条照样成立，只是等得久。它要改 ADR-011 §6「手动触发不插队」，单独成故事便于单独取舍。

**Independent Test**: 队里先排 5 个别的库，再发起提资带出的更新，看队列快照的行序与实际出队序。

**Acceptance Scenarios**:

1. **Given** 队里有若干普通排队行、一行在跑，**When** 提资带出一行，**Then** 它排在所有普通排队行之前、在跑的那行之后；
   快照的行序与出队序一致。
2. **Given** 队首是要独占的行（基线、重建、系统库），**When** 提资带出一行，**Then** 阶段屏障与独占规则照旧，提资行不越过阶段。
3. **Given** 先后两次提资各带出一行，**When** 出队，**Then** 按到达先后；同一个库已有带提资标记的排队行时只合并（优先名单取并集）。

### User Story 4 - 队列暂停时照样做这一次（Priority: P2）

部署里「增量同步」常关着（队列暂停）。人点「更新到最新」，只有提资带出的那几行（与它们的前置系统库）出队，别的行照旧不动，
做完队列仍是暂停。

**Why this priority**: 暂停是部署包的缺省状态；没有它，plant-ui 只能请人先恢复出队，那会放行队里所有库。与 Spec 041 同一条理由：
暂停防的是人不知道的情况下数据被动，而这一次是人当场点名的几个库。

**Independent Test**: 暂停队列，队里留几行普通行，发起提资带出的更新，核对哪些行出了队、暂停标志变没变。

**Acceptance Scenarios**:

1. **Given** 队列暂停，**When** 提资带出两行，**Then** 只有这两行与阶段早于它们的系统库行出队；快照里这几行写明放行的缘由；
   持久化的暂停标志不变。
2. **Given** 服务重启，**When** 还有没做的提资行，**Then** 不再放行（标记只在内存），再发起一次才重新打上。

### User Story 5 - 数据水位停在哪一次保存，说得出时刻（Priority: P2）

检查表的「数据水位」一列在落后时写出「停在 11-25 17:30 那次保存」，与「文件最新保存 11-26 10:42」并排。

**Why this priority**: 改动极小（时刻已经在水位行上），可以最先交付；但不影响放行。

**Independent Test**: 对若干库比较接口回的时刻与库文件里该会话的保存时刻。

**Acceptance Scenarios**:

1. **Given** 库已初始化，**When** 问节点状态，**Then** `library` 里带数据水位那次保存的写入时刻，与文件端的时刻同一个口径（带时区）。
2. **Given** 水位行上没有这个时刻（老行）或库没初始化，**When** 问，**Then** 这一格为空，不拿挂钟或别的时刻顶。

### User Story 6 - 其余单元让路（Priority: P3，可选）

一次提资涉及几个库。第一个库的提资单元做完了，它还有几十个被波及的单元要算；第二个库的提资单元（或另一个库的首次导入）排在后面等。
让第一个库余下的单元让到这些提资行之后再算。

**Why this priority**: 缺省一次只跑一批，所以只在「同时提资几个库」时有感；它要让一批任务在模型水位没盖时先收尾、再排一条后继，改动与风险都大于
前几条。先做前几条，看实际等待再定。

**Independent Test**: 两个落后的库各带几个提资节点同时发起，记下第二个库的提资节点答「是」的时刻，有无让路各跑一遍。

**Acceptance Scenarios**:

1. **Given** 这一批的提资单元已全部落盘、队里还有带提资标记的排队行，**When** 轮到算其余单元，**Then** 这一批先收尾（模型水位不盖），
   余下的单元进一条带根名单、只算模型的后继任务，排在那些提资行之后；后继做完才盖模型水位。
2. **Given** 队里没有别的提资行在等，**When** 轮到算其余单元，**Then** 不让路，一批做完。
3. **Given** 让路之后、后继做完之前进程重启，**When** 启动核对，**Then** 按现有规矩（模型水位落后于数据水位）排补算；不新增恢复路径。

### User Story 7 - 一次问多个节点（Priority: P3，可选）

提资清单有上百个元素时，一次请求问完，而不是上百次往返。

**Why this priority**: 今天 8 路并发够用（接口文档记的单次 19 – 41 ms）；元素很多时才成问题。

**Acceptance Scenarios**:

1. **Given** N 个参考号（N ≤ 上限），**When** 一次问，**Then** 逐个给出与单问相同的答复或各自的错误，互不影响；一个节点查不到不让整次失败。

### Edge Cases

- 提资节点是 ZONE / SITE，下面几百上千个单元：优先名单超过上限时不设优先，整窗照常做；回执写明。「可以提资了没有」仍答得出。
- 提资节点在库文件最新会话上已经没有了（被删）：逐个列在回执里，不让整次失败。
- 节点分属几个库：逐库独立判断与入队，一个库排不了不影响别的库。
- 优先单元里有生成失败的：照现有规矩记账、退避、任务收尾为部分完成；这几个节点答「不是」（单元失败）。
- 窗口规划退化（判不了哪些根被波及、全部按过期重算）：优先名单全部重算并排在最前；没被重算的根不认作落定。
- 任务跑到一半进程死掉：照现有规矩（写入标记停在 `writing` → 整库重新初始化）；期间这个库的节点一律不答「是」。此前已经基于
  「是」提交出去的那一次不受影响：答「是」的那一刻库里的行是对的。
- 两个人几乎同时对同一个库发起：只有一条任务，优先名单取并集；第二个人到时任务已开跑就按故事 2 场景 5 答。
- 库连接没落定（Spec 043 的派发门）：照排，回执说在等什么；提资标记不绕过派发门。
- 房间初始化门没过：不排，原因照报（与节点入库同一组原因码），不放宽。

## Requirements

### Functional Requirements

**A. 节点能不能提资（只读）**

- **FR-001**：`GET /api/v1/node/model-status` 的答复多一块（下称「提资就绪」，字段名见「契约草案」），回答这个节点连同全部后代
  在库里的数据行、模型行、房间边是不是都已是库文件最新那一版：是 / 不是 / 判不了。现有字段与判据不变。
- **FR-002**：答「是」的充要条件是三样同时成立——（a）库已初始化且数据水位不早于库文件最新会话；（b）节点子树里的每个生成单元
  都按这一版落过盘，或确实没被模型水位到这一版之间的改动波及，且没有失败悬着；（c）房间归属算完（与 `element/rooms` 的
  `settled = true` 同一份判法）。子树里没有生成单元时只看（a）。
- **FR-003**：库有任务在跑不再是一律「不下结论」的理由：FR-002 三样都能证明时照答「是」。（现有的 `verdict = updating` 不动。）
- **FR-004**：「不是」必须带原因码，逐一可辨：还没有数据 / 数据落后 / 数据正在写 / 单元还在等 / 单元失败 / 欠房间重算 / 房间体制没就绪；
  并带给人看的一句话。有任务在补它时带任务号。
- **FR-005**：给出单元计数：总数、已落定、还在等、失败；与 `units.total` 同一段枚举。计数不精确时标明。
- **FR-006**：判定与读取的先后要保证只偏保守：答「是」时，库里的行不早于判定所依据的那次提交（与 Spec 045 FR-013 同一条规矩）。
- **FR-007**：判不了就答「判不了」，不答「是」：水位读不到、生成单元解不出、账本与持久行都给不出结论、房间欠账评估不出来。
- **FR-008**：只读：不入队，不动水位、失败账、队列与暂停标志。这一块算不出来不让整条接口失败。读透形态答「不适用」。
- **FR-009**：`library` 多一格数据水位那次保存的写入时刻（水位行的 `applied_sesno_time`），读不出为空；`GET /api/v1/dbnums` 的行
  同样加上（可选）。
- **FR-010**（可选，US7）：批量形，一次问多个参考号，逐个给答复或错误。

**B. 提资带出的更新（入口）**

- **FR-020**：提供一个入口，收一组提资节点的参考号，由服务端解出所属的库，逐库判断并入队。形式待定：新路由（推荐），或给
  `update/execute` 加可选字段。见「待拍板」第 1 条。
- **FR-021**：逐库的判断与 `node/data-ingest`（Spec 041）同一套门、同一组原因码：执行范围、文件身份、房间初始化、系统库先行、
  增量开关、失败账。与人工执行不同的五处照搬：不清失败账、不放开模型重试、已停自动重跑的库不重试、文件回退不清库、
  按库给结构化回执。
- **FR-022**：逐库独立：一个库排不了不影响别的库；一个库的前置系统库过不去，这个库一行不排。
- **FR-023**：按库的状态决定排什么——没初始化：整库首次导入；数据落后：增量窗口（带优先名单）；数据已是最新而节点下有单元没落定：
  只补这几个单元；都已落定：不排。
- **FR-024**：不重复：同一个库已有排着的行时并入（优先名单取并集，打上提资标记），已有在跑的行时不打断，回执指向它并说明它覆盖
  不覆盖这几个节点。连着点几次只有一条。
- **FR-025**：回执逐库给：做了什么（排上 / 已在排 / 已在跑 / 排不了 / 不用排）、意图、任务号、队列位置、带出的前置系统库、优先单元数、
  暂停下有没有放行、排不了的原因码、给人看的一句话、两枚水位、失败账那一页。形状尽量与 `data_ingest.libraries[]` 一致。
- **FR-026**：解不出或已不存在的参考号逐个列出，不让整次失败。
- **FR-027**：同一次请求里的次序：增量在前，首次导入在后；阶段屏障要求系统库先行时以屏障为准。

**C. 优先**

- **FR-040**：优先名单 = 请求里属于这个库的提资节点子树中的生成单元（库文件最新会话上枚举）。随排队行在内存里，合并时取并集。
- **FR-041**：带优先名单的批次，模型半边把优先名单里被本窗波及的单元排在单元清单最前，先生成、先落盘；它们的落盘不排在别的单元后面。
- **FR-042**：优先名单里本窗没被波及的单元：规划一出来（且没有退化），FR-002（b）对它们就成立，不必等任务收尾。
- **FR-043**：其余单元照常在同一批里做完；模型水位、任务终态、失败处理、恢复路径与今天相同。
- **FR-044**：首次导入、整库重建没有提前放行；提资标记对它们只影响排队位置与暂停放行。
- **FR-045**：优先名单超过上限（数值待定）时不设优先，整窗照常做；回执写明「没有设优先」与原因。
- **FR-046**：窗口规划退化时：优先名单全部重算并排在最前；没被重算的根不认作落定。
- **FR-047**（US6，可选）：让路。优先单元全部落盘后，队里还有带提资标记的排队行在等时，这一批先收尾、不盖模型水位，余下被波及的单元进一条
  带明确根名单、只算模型的后继任务，按普通行排队；后继做完才盖模型水位。后继不重算本进程里已按这一版落盘的根。没有在等的提资行时
  不让路。让路期间进程重启，由启动核对按现有规矩排补算。
- **FR-048**：以上都不改变「同库严格串行」「数据水位只随数据提交前进」「模型水位只在每个生成单元都落库时盖」三条。

**D. 队列位置与暂停**

- **FR-060**：提资带出的排队行（增量、首次导入、只补优先单元的那一条，及其前置系统库行）带提资来源标记。标记只在内存，重启即失。
- **FR-061**（US3）：出队时，带提资标记的排队行先于同阶段不带标记的排队行；带标记的行之间按到达先后。正在跑的行不打断；同库串行、
  阶段屏障、独占、挂起、派发门照旧。队列快照的行序与出队序一致。
- **FR-062**（US4）：队列暂停时，带提资标记的排队行与阶段早于它们的行照样出队，别的行不出队；持久化的暂停标志不改，做完仍是
  暂停。与 Spec 041 的放行是同一个机制，多一种来源。
- **FR-063**：同一个库同一时刻至多一条带提资标记的排队行（合并）。让路排出的后继任务不带提资标记。

**E. 看得见**

- **FR-070**：任务行说得出优先单元做了几个 / 共几个；现有的 `units_done` / `total_units` 口径不变（含优先单元）。做了让路时，另带
  留给后继的单元数与后继任务号，后继行带它补的是哪一条。
- **FR-071**：队列快照的行上写明来源是提资、是哪几个节点带出的、暂停时放行的缘由。
- **FR-072**：`/health` 列出此刻带着提资标记的库与最近几次判定（与 `node_generate_ingest` 那一块同构）。

**F. 兼容**

- **FR-080**：新增的都是可缺席的格子与新路由；老客户端的行为与改动前一致。
- **FR-081**：客户端认旧后端的办法写进接口文档：没有「提资就绪」那一块 ⇒ 按库档；新路由回裸 404 / 405 ⇒ 退回两发 `update/execute`。
- **FR-082**：开关可关：关掉后入口答「没开」，不入队；「提资就绪」照答（它只读）。

### Key Entities

- **提资就绪**：一个节点此刻能不能提资的派生判断。按需算、不落库（与 ADR-099 同一条纪律）。
- **优先名单**：一次提资带出的更新里，某个库要先落定的生成单元。随排队行在内存里。
- **提资来源标记**：排队行上的内存标记，决定出队次序与暂停时的放行。与节点来源标记同一类东西。
- **后继任务**（只在做让路时有）：让路的那一批留下的单元，由它补完并盖模型水位。

## Success Criteria

- **SC-001（正确性，最要紧）**：只要对节点 N 答了「是」（依据会话 T），此后在库文件没有超过 T 的前提下，直连库读到的 N 子树的数据行与
  库文件在 T 上的解析逐元素一致，模型行与房间边与「整窗做完之后」再读到的一致。在 L3 夹具上对若干窗口、若干节点跑过，
  反例为零（包括：任务进行中、重启之后、规划退化、单元失败、让路之后）。
- **SC-002（快）**：本窗波及的单元 ≥ 50、优先单元 ≤ 5 的库上，从发起到这几个节点答「是」的用时，不超过「数据应用与提交」加「这几个
  单元重算落盘」的用时再加固定开销；相对整窗做完的用时有数量级上的差别。给出实测表。
- **SC-003（不退步）**：不走新入口时，现有 L3 套件全过；`update/execute` 的回执、队列次序、单元清单次序与改动前一致。
- **SC-004（队列）**：队里先有 5 行普通排队行时，提资行在正在跑的那一批结束后第一个出队；独占与阶段屏障的现有单测一条不改、全过。
- **SC-005（暂停）**：暂停下只有带标记的行与其前置行出队；暂停标志前后一致；重启后不再放行。
- **SC-006（重启）**：在优先单元落盘之后、任务收尾之前杀进程：重启后按现有规矩恢复，最终两枚水位都盖上；期间没有一次错误的「是」。
- **SC-007（时刻）**：抽若干库，接口回的数据水位时刻与库文件里该会话的保存时刻一致；老行为空。
- **SC-008（接得上）**：plant-ui 连新服务端，界面出现「提资范围已追平 · 其余后台继续」与两条进度；连老服务端，界面与今天逐格相同。

## 边界

- 只管「提资要用的这几个节点先落定」，不改变整库最终要做的工作量：全部做完时库的状态与不设优先时相同。
- 提资就绪是派生量：不建表、不进任何放行判据（生成、规划、水位都不读它）。
- 不替人做人工执行才做的事：清失败账、放开重试、回退清库。
- 不保证「答了是」到「rs-server 组包」之间库文件不再前进；那个窗口见「非目标」。

## 非目标（本期不做）

- 按元素判数据新旧（节点级的属性差分）。
- 改 rs-server。关死「检查与组包之间」的窗口要 rs-server 在组包时核对或回报它读到的数据水位；`datacenter_version` 里的「提资时的会话号」
  可以事后核对，另起一件事。
- 取消正在跑的批次；打断在跑的批次来让路。
- 首次导入的提前放行（用户已定：没有）。

## 待拍板（请 gen-model 一侧定；我的推荐写在前面）

1. **入口的形式**。推荐新路由（语义与 `node/data-ingest` 一脉相承，不清失败账、回退不清库，结构化回执）。另一种：给 `update/execute`
   加 `priority_refnos`，改动小，但它的「清账、回退重建」语义会跟着进来，客户端仍得自己先剔库。
2. **Assumption 1 成不成立**。成立：按本稿，调单元清单的次序就能提前放行。不成立（数据或模型行要到任务收尾才落盘）：提前放行就得靠
   让路（US6）来实现，那一条要从可选升为必做。
3. **插队**（US3）。要修订 ADR-011 §6。推荐做，范围限在「同阶段、只越过普通排队行、不打断在跑的」；不做的话前两条故事仍成立。
4. **让路**（US6）。推荐第一版不做，等有了「同时提资几个库」的实际等待数据再定。
5. **优先名单的上限**。建议与生成预检的确认阈值同一个量级起步（几十到一两百个单元），超过就不设优先。
6. **名字**。「提资就绪」那一块叫 `submission` 还是别的；来源标记的取值；路由路径。plant-ui 目前按暂定名 `publish_ready`（顶层布尔）与
   `library.applied_sesno_time` 留了读法，定稿后改成定稿的名字。
7. **数据已是最新、只缺模型时要不要由这个入口补**（FR-023 第三种）。推荐要：否则 plant-ui 只能请人去模型树上「重新生成模型」。
8. **批量预检**（US7）做不做。推荐先不做，等有了上百元素的实测再说。

建议的交付次序：US5（时刻，独立、最小）→ US1（按节点回答，含任务在跑时）→ US2（入口 + 单元清单的次序）→ US4（暂停放行）→
US3（插队）→ US6 / US7。做到 US1 时 plant-ui 就能按单元放行，只是「是」出现的早晚还看单元清单的原有次序；做到 US2 才稳定地早。
