## 一、为什么废弃旧 UI 架构

不是「旧代码写得不好」，是**旧结构到不了设计稿**。四条实测证据：

**1. 屏幕模型对不上。** 设计稿是屏幕流：项目选择（S5，1600×1000 全屏）→ 主工作台（S1，1600×1000 全屏）→ 模型更新（S2/S4，1040×720 弹窗）。画板尺寸本身就在说「哪些是屏幕、哪些是弹窗」。而代码里 `EditorTab` 有 23 个枚举值、注册了 18 个，**一次性任务与常驻视图平起平坐地摆在同一排页签里**：「防火封堵材料统计」「元件库」「模糊查询」和「三维视口」「模型树」是同一个层级。在这个结构上打补丁，永远排不出设计稿的样子。

**2. 没有统一的应用状态机。** 至少 8 个互不相干的 `States` 枚举，分散在 `lib.rs`、`shared.rs`、`ui_plugin.rs`、`app_state.rs`、e3d plugin 等处，其中**有两个同名的 `AppState`**。没人说得清「应用现在处于什么状态」，界面也就无法按状态组织。

**3. 界面与数据源绑死。** 控制台画一屏要套三层 `world.resource_scope`：

```rust
world.resource_scope(|world, mut state: Mut<ConsoleState>| {
    world.resource_scope(|world, console_open: Mut<ConsoleOpen>| {
        world.resource_scope(|world, mut command_entered: Mut<Events<..>>| {
```

这是「边拿数据边画」的必然结果。这样的代码既没法单独验证，也没法脱离 Bevy 运行。

**4. 反馈环太长。** rs-plant 有 60 个直接依赖（29 个 git fork）、1483 个包、186 MB 产物；改一行界面代码的增量构建实测 30 秒到 4 分半。ui-next 沙盒 434 个包，同样一行改动 **1.5 秒**。差了两个数量级。

## 三、目标架构

### 三层外壳

| 层 | 判定标准 | 内容 |
|---|---|---|
| 屏幕 | 互斥的全局阶段 | 登录 → 项目选择(S5) → 主工作台(S1) |
| dock 常驻视图 | **需要与三维视口同屏可见** | 模型树、三维视图、命令行、日志、属性、**任务队列(S12)** |
| 任务窗 | 有头有尾、完了就关 | 模型更新(S2 预览与确认)、设置(S6)，以及后续 S7/S9/S10、S13（原 S11 模糊查询，07-27 顺延） |

**任务队列是 07-27 晚加进 dock 的第六块，模型更新的执行进度(S4)同时从任务窗迁了出去**（ADR-0011）。
起因在服务端：手动与自动两条来源合流成一条数据批次队列之后，「有头有尾、完了就关」这条判定标准
对执行进度不再成立——同一个 dbnum 会有两个进度画面，而向导那个只看得见「本次运行」，前面还排着
别的库时它会摆出一个说不出自己为什么不动的界面。反过来，队列符合 dock 那条判定：它一直在跑，
你希望余光能扫到。这是三层外壳这套分类第一次被真实需求推着重分一次类，分完之后两条判据都更站得住。

### 数据流

```
SurrealDB (本地测试库)
   |  SUL_DB.query(...)         <- aios_core 的全局静态句柄
   v
数据层：把查询结果整理成每屏的 Vm 结构（装 aios_core 原生类型）
   |  &Vm 进
   v
UI 层：纯绘制函数，不认识 Bevy、不认识数据库
   |  Vec<Cmd> 出
   v
派发层：独立应用里直接执行；接进 Bevy 后转成 Event / Command
```

三维视口对 UI 层而言**只是一个 `TextureId`**——已核实：Bevy 把相机渲染到 `RenderTarget::Image`，再经 `EguiUserTextures::add_image` 注册给 egui。所以独立应用里先给占位纹理，接进 Bevy 后换成真相机，UI 代码一行不改。

### 新项目目录

```
D:\work\plant-code\old\plant-ui\
  Cargo.toml              workspace
  .cargo/config.toml      源替换指向 vendor/registry/
  crates/
    plant-ui/             egui 0.35 + 组件层 + 各屏绘制 + Vm 定义
    plant-ui-data/        SUL_DB 查询 -> Vm；不含任何绘制
    plant-ui-app/         独立可执行：eframe + 上面两个 + 占位视口
  vendor/
    registry/             cargo vendor 产物（只读、带校验和）

  design/                 从现仓库带过来：.pen 源文件、DESIGN-SYSTEM.md、画板导出
```

可编辑源码树不能直接混进 `cargo vendor` 的目录源（目录源要求每个子目录都带 `.cargo-checksum.json`），所以只读部分放 `vendor/registry/`、可编辑部分放 `vendor/rs-core/`，都在 `vendor/` 下但机制分开。

新项目独立建 git 仓库，从 M0 起小步提交；本计划文档同时保存一份在新项目 `docs/plans/` 下。

### vendor 分类

| 依赖 | 方式 | 说明 |
|---|---|---|
| 第三方不改的 | `cargo vendor` 只读 + `.cargo/config.toml` 源替换 | 可复现、可离线；改了会报校验和错误 |
| 自家代码 `aios_core` | `vendor/rs-core/` 可编辑源码树 + path 依赖 | **拷贝自 `rs-core-pin` 钉版**（= git rev 5667b70 + get_world 顺延修复，与 gen-model 当前 patch 一致），不是脏检出的 `plant-code\rs-core` |
| Bevy 生态 fork | **M3 才引入**，届时以可编辑源码树进入 | 里程碑 1 用不到 |

`vendor/rs-core` 与 `vendor/forks/*` 是 path 依赖，也就是 workspace 成员：**不要跑 `cargo fmt --all`**，它会把这几棵树整个重排（一次 183 个文件），钉版差异从此看不清。格式化只对自己的三个 crate 跑：`cargo fmt -p plant-ui -p plant-ui-app -p plant-ui-data`。

#### `vendor/rs-core` 的改动记录（换钉版时要重放）

| 位置 | 改动 | 缘由 |
|---|---|---|
| `rs_surreal/query.rs` `get_named_attmap_with_uda` | `pub(crate)` -> `pub` | UI 版属性表 `get_ui_named_attmap` 会把引用与未设值都压成 `StringType`，属性面板判「哪些字段可编辑」需要压之前的原始类型。该函数带 `#[cached]`，多取一次不额外打库 |
| `lib.rs` `init_surreal` | `.build().unwrap()` -> `.build()?` | 读不到 `DbOption.toml` 时原先直接 panic，整个应用连一条错误都留不下就没了。函数本来就返回 `anyhow::Result`，改成 `?` 之后这条失败会顺着数据线程回到面板的错误态与命令行 |
| `rs_surreal/mdb.rs` `get_mdb_world_site_ele_nodes` | `SUL_DB.query(&sql).await.unwrap()` -> `?` | 同上。这是模型树根层查询的第一跳，M1-7 验收错误态时就是从这里逼出来的——把 `v_port` 指到无人监听的端口，原先是 panic 而不是错误态 |
| `rs_surreal/mdb.rs` `get_mdb_world_site_ele_nodes` | 根层查询去掉 WORL 那一跳，改成 `pe where noun='SITE' and dbnum in $dbnos` | 原查询是 `MDB -> WORL -> SITE` 三跳，中间那跳要求每个设计库都有世界元素，而同步经常不写它：`admin_sites/ams7997-e3d31` 那个库 `WORL` 表 0 条、`pe` 里也没有 `noun='WORL'`，8009 内存库里 db 8000 的真实世界 `pe:16192_0` 同样缺。缺的只是那一个节点——15 个 SITE 与指向它的 15 条 `pe_owner` 边都在——但整棵树因此全空。SITE 自己带 `dbnum`，够定位根层 |
| `rs_surreal/mdb.rs` `query_mdb_db_nums` | 同上，由 `WORL` 改为按 `SITE` 取 dbnum 去重 | 与根层同源，否则状态栏的库标识会和树对不上：树有 15 个 SITE 而库标识是空的。顺带得到一个好性质——MDB 里声明了却一个元素都没同步过来的库自动不出现（`/ALL` 在 8022 上声明 29 个库，实际只报 7997） |
| `rs_surreal/query.rs` | 新增 `per_element_caches!` 宏 + `clear_all_caches_wholesale()` | 「取回工作」要整进程缓存失效：增量是 gen-model 那个进程应用的，本进程拿不到逐 refno 明细，逐项失效无从下手；且根层 / 库号 / 可见实例三张表的键里没有元素本身，只有整表清才回得来。宏把逐元素缓存清单收拢成一份，批量失效与整体失效共用，新缓存漏加一边会静默失效的坑就堵住了 |
| `prim_geo/category.rs` `convert_to_brep_shapes` | Extrusion 分支补 `d.verts.len() <= 2` 早退（与 Revolution 同一道卡） | 少了它，轮廓解不出来时会造出空挤出体：`gen_occ_shape` 必然拒绝，但它已经被 hash、落库、挂上 geo_relate——且所有空轮廓算出来是同一个 hash，一整批构件会共用这一条建不出形状的几何 |
| `rs_surreal/index.rs` `define_pe_index` | 补 `DEFINE INDEX pe_owner_index ON TABLE pe COLUMNS owner` | `pe.owner` 一直没索引，按 owner 过滤是全表扫。在 8009 上实测（200,873 行 `pe`）：`SELECT count() FROM pe WHERE owner = pe:24381_101405` 命中 50 行却要 **1,649ms**（扣掉 ~350ms 的 CLI 连接开销 ≈ 1.25s），建索引后降到基线以下、量不出来；索引构建一次性 6.9s。旁边那个 `define_owner_index` 名字很像但建的是 `pe_owner` **边表**的 `(in, out)`，不顶用——这是它一直没被发现的原因 |
| `rs_surreal/index.rs` `define_pe_index` | 补 `DEFINE INDEX pe_noun_dbnum_index ON TABLE pe COLUMNS noun, dbnum` | **模型树根层查询原本要 2.2 秒**，是 plant-ui 启动后第一件事。拆开量（同一实例，扣 320ms 基线）：`MDB`/`CURD` 取 dbnos 20ms、`children_count` 子查询 ~0ms，全部时间都在 `pe where noun='SITE' and dbnum in $dbnos` 这一跳 = 2,165ms。**元凶是既有的 `pe_dbnum_index` 反而拖后腿**：dbnum 只有 3 个值、覆盖全表，选择性极差，但规划器偏挑它——走 dbnum 索引 2,779ms，纯全表扫（`noun='SITE'` 单条件、noun 无索引）只要 955ms。补这条复合索引后该跳降到 **22ms**，根层端到端 2,552ms → 421ms（净 2,155ms → 101ms，**21 倍**）。试过的单列 `pe_noun_index` 被复合索引完全覆盖（前导列），已撤，不要重复加 |

`init_surreal` 与 `get_mdb_world_site_ele_nodes` 那两条 `unwrap` 是 M1-7 验收错误态时顺手改的，当时没进表。**这类改动不进表就等于不存在**：换钉版时按表重放，表里没有的会静默丢失，而丢失的形态是「某天又开始 panic 了」，很难回想起是重放漏了。

两条索引的**代价还没量**：`pe` 每多一条索引，写入就多一份维护，而写吞吐本来就是 ams7997 报告的 P1（157k 行时掉到 650 行/秒）。下次基线化大库前顺手对一下；真要是明显变慢，可以改成「解析前 `REMOVE INDEX`、解析完 `DEFINE INDEX`」。另外 `pe_dbnum_index` 现在是**待观察的删除候选**——根层那一跳已经由复合索引接管，而它在低选择性场景下会把规划器带沟里；但别急着删，先确认没有别的查询靠它。

也不给每个视图都凑齐四态——造一个永远不出现的态就是摆假状态，与外壳「宁可少一格也不摆假数字」是同一条：

| 视图 | 未初始化 | 加载中 | 空 | 错误 |
|---|---|---|---|---|
| 模型树 | 无：启动即发连接请求，`TreeVm` 默认值就是 `Loading` | 有 | 有：当前库下没有 SITE | 有，「重试」= 重连 |
| 属性 | 有：尚未选中元素 | 有 | 无：属性表至少带 TYPE 与 NAME | 有，「重试」= 重查当前选中 |
| 日志 | 无 | 无：日志是 App 自己写的，不查库也不会失败 | 有：缓冲空与筛选后空两种文案 | 无 |
| 命令行 | 无 | 无：输入框始终可用 | 有：空会话只显示输入框 | 无：命令错误写入会话 |
| 三维视图 | 无：占位图启动时同步载入 | 无 | 无 | 有：纹理载入失败 |

因此 `PropsVm::Empty` 改名 `Uninit`——它说的是「还没轮到它」而不是「查完了没有」。M3 接回 Bevy 后，相机还没给出渲染目标的那一段才会有三维视图真正的未初始化态。

加载中画 egui 的 `Spinner` 而不是静态的转圈字形：不转的转圈图标看着就像界面卡死了。顶距按内容块高度算居中而非固定值——面板从命令行那样的窄条到整根属性栏都有，固定顶距会在矮面板上贴边、在高面板上浮到上三分之一。**已知不足**：块高只按一行正文估算，错误态那种换行到三行的文案会被压到中线以下约两行；单行的态居中是准的。

验收方法留一笔：错误态在这套数据上没有自然的触发路径，是把 `DbOption.toml` 的 `v_port` 临时指到一个没人监听的端口逼出来的，全程不碰任何数据库；三维视图的错误态则是把占位图临时改名。属性的错误态与模型树的空态在本项目的库上够不着（库里实有 3 个 SITE，而属性查询失败要求连着库的同时查询失败），它们与已验证的几态走同一个 `pane_note`，差别只在接线。

#### M2-4 的施工图与预期收益（实测，2026-07-27 下午）

**先说结论：别拿「编译更快」当理由，那个收益只有一秒左右。** 实测 `rs-plant` 自己这个 crate
重新 `cargo check` 是 **3.6s**（碰 mtime 触发，跑两次 3.58 / 3.62，日志确认了 `Checking rs-plant`）；
而 79 个依赖里**只有 4 个是纯旧路径的**（`egui-toast` / `egui_data_table` / `indexmap` / `js-sys`），
bevy 全家、surrealdb、parry 这些占掉冷检查约 50s 的大头宿主自己也在用，一秒都省不掉。
删掉四分之一到一半的源码，省的是 3.6s 里的一两秒。要做这件事，理由得是风险表里那条
「两处代码分叉」和「别让后来人在一万多行没人跑的代码里找路」，不是构建速度。

**可删体量的下界是 14132 行 / 28%**（从宿主入口做模块级传递可达性算的）。说下界是因为
文件粒度的可达性会高估——一个文件只要有一处被引用，整份就算活的。完全不可达的整棵子树里
最干净的几块：`visual_nodes` 3362 行、`interactions` 756、`wasm_api.rs` 43、`renderer` 29、
`assets.rs` 13、`state` 8；大比例不可达的还有 `settings` 74%、`utils` 68%。

**边界在哪，是拿编译器问出来的，不是估的。** `editor_ui/mod.rs:63` 有一行
`pub use ui_plugin::*;`——`ui_plugin` 就是 802 行的旧 dock 外壳。而 `plant_ui_host.rs`
从 `editor_ui` 只拿两个常量（`MAIN_SCENE_LAYER` / `OLD_SCENE_LAYER`），它们恰好住在 `mod.rs` 里，
于是这一行 glob 把整个旧外壳（含 `widgets` 2165 行、`theme` 1838 行）一起挂在了宿主身上，
静态分析看上去全是活的。把这行注释掉跑一次 `cargo check`（改完立刻 `git checkout --` 还原，
未留下改动），得到 16 个错误，边界一目了然：

| 报错方 | 缺的东西 | 性质 |
|---|---|---|
| `editor_ui/editor_tab.rs:8`、`editor_ui/egui/mod.rs:1` | `EditorUiRef` / `EditorUiReg` / `EditorUi` | 旧 dock 自身的基础设施 |
| 11 个插件（`console` / `e3d` / `model_review` / `review_drawing` / `material_statistic` / `pbs` / `version` / `status` / `angle_measurement` / `distance_measurement` / `measure`） | `EditorUiAppExt`、`EditorUi`、`check_main_scene_view_tab` | 全部是为了注册旧 dock 页签 |
| **`plant_ui_host.rs`** | **零个错误** | **宿主不需要旧外壳的任何东西** |

宿主对 `editor_ui` 的全部依赖就四项：`camera_plugin::focus_camera`、`shared::{...}`、
`viewer::{interact, select}`、加那两个常量。`editor_tab` / `ui_plugin` / `widgets` / `theme`
一个都不碰（`e3d_plugin/plugin.rs` 那句 `use ...editor_tab::EditorTab` 与两处
`editor_tab_by_trait` 调用都在它自己的旧分支里）。

**所以 M2-4 的顺序是清楚的**：旧 dock 外壳眼下唯一的消费者就是那 11 个插件的页签注册代码，
而摘掉它们本来就是 M2-3「仅删 UI 保留逻辑」的活。**先做 M2-3，`editor_ui` 的 dock 外壳就会
自动掉到零引用**，那时再删它不需要判断，编译器会证明。反过来先删外壳则要同时改 11 个地方。
收尾时把那几个 scene layer 常量挪到 `consts.rs` 一类的中立位置，`editor_ui/mod.rs` 才能整个消失。

[`view3d-migration.md`](view3d-migration.md)。**本节此后只作历史记录，不再更新。**

顺带修正一处会误导人的读法：M3-3 那条「视口拾取只有宿主里有真行为」如实描述了现状，

`Cmd::PickViewport` / `Camera` / `ResizeViewport` / `Model` 四条全是空实现，而绘制层每帧

#### M4-4 半天里换掉了两处根据（回填于 2026-07-28 凌晨）

上面那条「做得最扎实」写于 07-27 下午，那时它是三步向导对三个接口。到当晚为止，
根子上换掉的有两处，各有一份 ADR 记着；施工顺序与逐项落点在
`docs/plans/task-queue-rollout.md`，这里只记与本计划相干的部分。

**一、执行进度整体搬出任务窗，进了 dock（ADR-0011）。** 向导砍成预览与确认两步，
第三步迁到常驻的「任务队列」视图，新文件 `crates/plant-ui/src/task_queue.rs`——契约、
Vm、行推导与绘制放一处，与 `model_update.rs` 同源，**不进 `workbench/`**，那一层按模块
注释是「不认识数据源」的纯绘制。连带退役三样：ZONE 分桶（变化树从 dbnum → ZONE → 交付
单元三层收成两层）、409 与 422 两种失败形态（执行请求一律入队）、以及「运行」这个词本身
——队列里一行是一个数据批次，不再是一次手动更新的执行实例。状态栏加「队列 N」/
「队列 N · 已暂停」，**没读到快照时那一格整个不画**：「队列 0」与「还没拿到第一份快照」
是两句话，这与外壳一贯的「宁可少一格也不摆假数字」是同一条。

**这里留下一处与 M2 同形的中间态，要盯着。** 向导确认之后改成「回执进日志 + 关窗 +
跳队列页签」，于是 `Vm::Running` / `Run` / `RunVm` 与第三步那整段绘制**再没有构造点**，
成了编译得到、跑不到的死代码（`main.rs` 里那条 `GET /tasks/{id}` 轮询通道同样没了发起方，
源码上已按此注明）。M2 那节花大力气讲的「运行时死、编译期活」——删除的验证手段本身失效
——这次是我们自己刚造出来的一份，区别只在施工单上写明了它随客户端第 3 项「砍第三步」
一并退役。**没退役之前它就是同一种债**。

**二、本期执行范围改由当前 MDB 定（ADR-0013）。** 过去的范围是「项目目录里认得出的库 ×
类型白名单 × 手写的 `manual_db_nums`」，现在是「当前 MDB 在 CURD 里声明为 DESI 的那些库」。
对 AvevaMarineSample 这是 294 行收成 29 行。客户端这侧三处改动：

- `project_identity()` 多返回一个 MDB 名（`to_e3d_name(&opt.mdb_name)`，带前导 `/`），
  `preview` / `execute` 两个请求都带上 `mdb`，服务端在 `ManualUpdatePreview.mdb` 里回显，
  向导副标题写成 `AMS-8009 · MDB /ALL · 仅扫描当前项目`。**MDB 名由客户端给是有意的**：
  范围既然由 MDB 定，界面显示的范围与服务端真跑的范围就必须同源；两侧各有一份
  `mdb_name` 配置，让服务端读自己那份，此刻都写 `ALL` 纯属巧合，一错开就是静默分家。
- 新增第三种「不执行」——`not_in_project`（够不着）。`/ALL` 声明的 29 个 DESI 里只有 20 个
  的文件在当前项目目录下，另外 9 个（AvevaCatalogue 的模板与标准库）在别的项目里，而扫描
  按契约只走当前项目。它不叫「文件缺失」：缺失是登记过的文件不见了、要阻断；这 9 个从没
  登记过，本期只是碰不到，不阻断也不执行。合成一行的话，那 9 个模板库会顶着「已阻断」
  出现在界面上，人会去找根本不存在的故障。
- 范围行上三个数分开摆：`20 个 DESI 设计库在范围内 · 9 个 MDB 声明但项目内无文件 ·
  N 个非 DESI 已排除`。**MDB 之外的设计库连行都没有**——上面那个 294 → 29 就收在这里，
  靠「在范围内」这个数与 MDB 声明数一对就知道差在哪。够不着的那些也不计入「有没有待办」，
  否则每次预览都在，「已是最新」这个终态永远到不了。两条单测钉着这两件事。

**契约面从 3 个接口长到 10 个**：`POST /update/preview`、`POST /update/execute`、
`GET /queue`、`GET /tasks?limit=200`、`GET /health`、`GET /dbnums`、
`GET /update/pending-units`、`POST /queue/pause`、`POST /queue/resume`、
`POST /model/ensure`，外加 `/api/v1/ws` 上按 task_id 分桶的逐单元明细。
队列面板的一次轮询把其中五份只读接口打包成一次事件交出去（分开更新会出现「队列已经空了、
顶栏摘要还说有一条在跑」这种自相矛盾的中间态），有活一秒一拍、全空五秒；
**排队与运行中的行以 `/queue` 为准**，
`/tasks` 只补计时与终态历史——服务端把 `limit` 钳到 200，拿它当队列来源会在积压态下截断。
风险表「数据边界」那条的结论不变（两仓库不共享类型、只共享 JSON 契约），但**面大了三倍多**，
而且这半天里逮到两处契约错位，都是「解错了不报错、只静默空掉」的形态：`Outcome.batches:
Vec<_>` 实为单数 `batch: Option<_>`（旧形状带 `serde(default)`，终态摘要会整块消失）、
`Accepted` 实为 `Enqueued` 入队回执（三个必填字段会让 execute 的响应整个反序列化失败，
「确认并开始」按下去只得到一个看不懂的 internal 错误页）。**这两处不是被测试拦下的**，
是对着服务端 spec 逐字段核出来的——现有的反序列化用例守的是「字段缺了要炸」，
守不住「字段换了形状」。

**验收只做到一半，欠的那一半原因很具体：真服务没换。** 替身服务（`output/queue-mock.ps1`，
按 `QUEUE-FIELD-MAP.md` 的样例数据搭）上逐行对过 S12 / S12-B，截图在 `output/` 下。
真服务这边，8021 上跑的仍是 21:05 启动的旧版（`version 0.1.3`，二进制 19:42 构建，而服务端
那片 21:38 才提交）：`/queue` 直接 404，`/health` 没有 `started_at` / `gen_spatial_tree` /
`queue_paused`，`/dbnums` 没有 `anomaly` / `blocked` / `excluded`，`/tasks` 空表。
于是这一晚真正验到的是「客户端对上旧服务端」那一半——整次轮询因 404 失败，面板说
「读不到任务队列」并附上原因，状态栏那格整个不画，「没读到快照就不摆一个假的 0」这条口径
在真服务上兑现了（`output/queue-live-old-server.png`）。**排队 / 合并 / 冻结的实况仍然欠着**，
要等 8021 的重启窗口或者复制数据目录另起端口；**不要在 8009 实库上再起第二个进程**——worker
是无条件 spawn 的，两个消费者并发冻结会破坏 FIFO 串行，还可能重复应用数据批次。

**这条线上还欠着的**——只有第一条是本仓自己能了结的，其余五条都要 gen-model 侧先动：

| 欠项 | 说明 |
|---|---|
| 砍第三步 | 上面那段死代码退役，施工单客户端第 3 项 |
| ADR-0006（预览改 202 + `task_id`）押后 | `MODEL-UPDATE-FIELD-MAP.md` 的 S2-A 整节依赖它，押后期间保持诚实等待态、其余各行先不实现 |
| 真服务验收 | 见上，环境已定、没搭 |
| 「欠 N 个单元」今天会显假账 | 服务端 `ensure_model_generated` 成功后不清 `model_update_pending` 的 regen_root 行（8000 上实测 4 条躺了 4 小时以上）。界面的处置是把这句写进那枚「重试」的悬停提示——按下去生成真会跑、上面的数字不动，不说的话它在人眼里就是一枚按了没反应的按钮。服务端补 `clear_regen_work` 之后连注释一起摘 |
| 自动 watcher 还没认 MDB 范围 | `should_process_database` 是手动与自动共用的门，MDB 范围只加在手动路径上。两条来源已经共用一条队列，这个口径差迟早要抹平 |

#### 已消化的四条（回填于 2026-07-27 下午）

- **依赖体量**：不成立。增量 `cargo check` 6.1s，闸门 15s。
- **egui 桥接**：已过。`bevy_egui35` 打通，Bevy 未动，两条备选都没用上。
- **组件层迁移**：已过（M0-6）。唯一断点是 `set_style` -> `all_styles_mut`。
- **数据边界**：已定。边界就是 `gen-model` 的那三个 HTTP 接口，两仓库不共享类型、只共享 JSON 契约，
  契约由 `model_update_api.rs` 的反序列化测试守着。
  **07-28 补注**：接口已长到十个，结论不变但面大了三倍多，而那道守卫的边界也量出来了——
  它守的是「字段缺了要炸」，守不住「字段换了形状」，当晚两处静默空掉的错位是对着服务端
  spec 逐字段核出来的，不是测试拦下的。见 M4-4 那节。

**「删除误伤」这条仍然活着，但形态变了**：原先认定的具体形态（两处跨插件事件注册）经核对不成立，

真正还在的风险是另一种：`plant-ui-host` 让整条旧路径进入「运行时死、编译期活」的中间态，
没有人再跑它，也就没有人会发现删错了什么——**删除的验证手段本身失效了**。
`cargo build` 通过（M2-4 的验收标准）在这个状态下已经证明不了多少。
