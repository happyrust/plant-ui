# 面板按「段级缺席」降级，不问服务端是哪一代

任务队列面板要在两代 gen-model 之间并存：新服务端带全字段，老服务端缺一批（增删改三数、`UnitKind` 刚体前移、
房间段、模型判决……）。**决定：界面不探测服务端版本、不做能力协商，只对每一格问「这次给了没有」——给了就画，
缺了就整段不画**，绝不把缺省的 0 / 0 / 0 或空数组画成「无变化 / 正常」。判据落在结构本身：契约字段一律
`#[serde(default)]`，纯函数（`BatchResult::change_breakdown`、`Outcome::transform_roots`、欠账段三态判读……）
把「缺席」与「真零」在同一处分开，调用点只认它们的返回。

这样做是因为版本探测会把「服务端能力」复制成客户端的第二处判断，两处一旦不一致，同一块面板就会半新半旧地
自相矛盾，而且没有任何东西会报错（ADR-0025 已为模型来源挡过同一类「一次装载混两个源」）。段级缺席则是局部的、
可组合的：任意字段组合缺席都自然退化，升级服务端时界面无需改一行。

## Considered Options

- **版本 / 能力协商**（`/health` 报一个 feature 集，界面按集开关段落）：多一处必须跟服务端同步演进的版本矩阵，
  漏一格就是静默错画；被否。
- **按 `/health.data_face` 之类状态自行推断**：与 ADR-0025 否掉的「自动探测」同病——服务端一抖，界面悄悄换形态，
  日志里什么都没有。

## Consequences

- 每一个「待新增」字段落地时，界面只加「给了就画」的一段，不碰版本判断；房间段（计划
  `docs/plans/2026-09-09-task-finished-detail-plan.md` V3）就按这条等 gen-model S8/T4。
- 代价是界面永远说不出「你连的是老服务端」这句整体判断——它只知道这一格空着，不知道为什么空。这是自觉接受的：
  整体版本不是界面该负责的事。
- 先例：欠账段三态（`pending_endpoint_retired`，09-08 计划 U1）、模型判决老服务端不给整格不画（ADR-0025 邻接）、
  增删改三数分解缺席降级（计划 `2026-09-09-task-finished-detail-plan.md` §2、QUEUE-FIELD-MAP.md §1.5）。
