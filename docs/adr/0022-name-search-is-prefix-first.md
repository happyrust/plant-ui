# 按名称搜索：前缀跟着输入，包含匹配跟着回车

标题栏搜索框按名称找元素时走两条路。**前缀匹配**是默认那条，跟着输入每敲一下发一次，落到 `pe.name` 索引的范围扫（`name >= 前缀 AND name < 前缀+最大字符`）；**包含匹配**是补搜，只在前缀一无所获时由用户按回车显式发起，并且只在当前 MDB 声明的设计库（`dbnum IN …`）里跑。长得像参考号的输入根本不打库，直接交给树定位；挑中任何一条候选都走 ADR-0014 那条既有路径。

分成两条是因为代价差着四个数量级，而这个差距不是估的。AMS 库（`pe` 878 万行、其中 625 万行有名字）上实测：前缀范围扫 1~2ms，查询计划是 `Iterate Index`；同一个词改用 `string::contains` 全库逐行比对要 37 秒；限定到当前 MDB 的三个设计库（38 万行）之后是 5~7 秒。所以包含匹配可以有，但不能跟着按键走，也不能不限范围——这两件事任一成立，搜索框就变成一个每敲一个字母卡半分钟的东西。

限范围的写法也是被规划器逼出来的：`WHERE dbnum IN $dbnums AND string::contains(…)` 会因为那个函数把整个 `WHERE` 判成不可索引，连 `pe_dbnum_index` 一起放弃，于是又退回全表扫。现在先用子查询按 dbnum 把库筛出来，再在外层比名字，两步各归各的。

代价要在界面上说出来，不能让人拿几秒钟的等待去换一个惊喜：下拉里先摆出「回车逐条搜名字里含它的（N 个设计库，要等几秒）」，跑起来之后再摆「正在逐条比对 N 个设计库…」。前缀那条不限 MDB——名称索引对全库一样快，而库里确实有能查到、树上却没有的元素；它们标「树外」，选中后照常显示属性，不切换 MDB（同 ADR-0014）。
