# 进度的分子分母都放在任务记录里，不放在事件流里

要在 S2-A 与 S4 上画出一条**确定态**的进度条，就得有分母。摸了一遍两侧代码之后，
原先设想的两条路都不成立。

`MODEL-UPDATE-FIELD-MAP.md` 早先写的是「分母 24 = 预览的 23 个新单元 + 1 个待重试单元」。
这个加法两个方向都会偏：执行开始时会重新扫描，预览之后新产生的会话自动并入同一个数据批次
（`merged_sesnos`），并入的会话带来新单元，分母偏小；而 `merge_unit_worklist` 按
`(dbnum, root_refno)` 去重，待重试的单元若本窗口又被改到，它和新单元塌成一条，分母偏大。

退一步让后端发一条带 `total` 的阶段事件也不够。事件不重放——`seq` 是连接内单调的序号，
不是可回放的游标。晚连一秒、断一次线，那条事件就永远拿不到了，进度条从此没有分母。

所以：**四个计数（`total_batches` / `batches_done` / `total_units` / `units_done`）存进
`TaskEntry`，跟着 `GET /api/v1/tasks/{id}` 一起返回。** 服务层那个
`ManualUpdateProgress` 回调现在只做 `tasks.bump_events(&tid)`，改成按事件类型分别累加即可。
真实工作量 `worklist` 与排序后的 `dbnums` 都在各自的循环开始前就已经算好了，是权威值。

## Considered Options

- **前端拿预览值相加**：契约一个字段不动。但分母在两个方向上都会偏，只能在界面上用「约」
  或 `≥` 糊过去，而这恰恰是本仓库最不允许的那种数字。
- **后端发一条带 `total` 的阶段事件**：比相加准。但它和逐单元事件走同一条不重放的通道，
  断线之后拿不回来，等于把分母的可得性绑在了连接的运气上。
- **只显示已完成计数，不要分母**：最诚实，也最省事。但那是活动指示器，不是进度条。

## Consequences

- **断线降级的形状变了。** 进度条的数据源是轮询，WS 断开不影响它的准确性；要降级的是
  **列表区**，不是那条条。单元行明细缺多少由 `events_seen` 减本端已收算出来，那个数
  从此只用来解释明细的缺口，不再拿来反推进度。ADR-0005 里「条冻结在最后已知值」的设想作废。
- **`events_seen` 换算不回进度**，别再试。它把四类事件混在一起数，而 `DataBatchFinished`
  有两个 emit 点，反推只能靠猜。
- **有了权威分母，就可以给百分比了。** `MODEL-UPDATE-FIELD-MAP.md` 里「没有百分比」那一行
  的前提是「契约里没有分母」，前提变了，结论跟着变。**ETA 仍然不给**：一个 BRAN 和一个
  EQUI 的生成耗时差一个数量级，外推出来是猜。界面上要说清这是单元数进度、不是时间进度。
- **阶段一的分母要求后端补事件。** 现在有四条早退路径产出了 `DataBatchResult` 却一条事件
  都不发：同 dbnum 多文件、文件回退、首次按需初始化（还是成功的 `Applied`）、`Ok(None)`
  的无事可做。修法不是逐个补 `emit`，而是把「开头发 `Started`、每条出口发 `Finished`」
  包到 `execute_one_dbnum` 的函数边界上，让「每个批次都有头有尾」成为不变式。
- **预览的扫描循环要先排序。** 现在它走 `IndexMap` 的 WalkDir 序，而最终结果在返回前按
  dbnum 排过；照事件顺序堆出来的列表会在预览完成那一瞬重排。执行侧本来就在循环前
  `sort_unstable()`，两条路径对齐即可，前端照事件 append 就行。
