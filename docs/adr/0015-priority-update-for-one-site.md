# 指定 SITE 的优先更新：收窄扫描范围，两个阶段都要提前

> **状态：草稿，未定案。** 十题里有三题是 60 秒超时自决的（Q1 / Q2 / Q5），
> 下面逐条标了出来。每一条推翻只需一句话。本文只记设计，一行代码没写。
>
> **2026-08-07 追记（ADR-0017）**：Q7「向导里不加收窄入口」**已作废**——向导预览重构为
> SITE 视图后，向导本身就是子集选择的主入口。「Consequences」gen-model 第 1 条
> （execute 加 `dbnums` 过滤）由 gen-model ADR-020 提前兑现。本文其余结论不动。

「我在模型树上指定一个 SITE，让它对应的库先更新」——这是人对着一个几百行的队列时
最自然的诉求。但它落到当前架构上有三处对不上，先把事实说清楚，再谈怎么做。

## 三个改写题目的事实

**一、数据应用切不到 SITE。** 数据应用的最小单位是（dbnum, 会话号区间）。会话是**库级**
的写入记录，一个会话里混着这个库所有 SITE 的变化；水位是库级单调值，只前进不后退。
所以「只把这个 SITE 的数据更新过来」在阶段一无法表达——在树上点一个 SITE、解出它的
dbnum，等于选中了那个库的**全部**待应用会话。**SITE 在这里只能当选取入口，不能当执行范围。**

**二、「穿插进正在跑的 task」没有落点。** 队列是单 worker FIFO，`freeze_next` 取队首；
批次一开跑会话区间就冻结（gen-model ADR-011 §5）。服务端没有中止接口，也没有单条取消
——暂停都只能「挡出队，正在跑的那一批跑完为止」。往一个已冻结的批次里注入工作，
直接破掉那条不变式。能做的是「提到队首，当前这批跑完下一个就是它」。

**三、SITE → dbnum 不需要猜。** `pe` 表直接有 `dbnum` 列，模型树根层查询本来就是
`select … from pe where noun='SITE' and dbnum in $dbnos`（rs-core `rs_surreal/mdb.rs`），
只是 `EleTreeNode` 没把它取出来。成本是在 select 列表里加一列。
（refno 前缀确实是 `dbnum + 16384`——`pe:24381_*` 对 db7997、`pe:24384_*` 对 db8000
——但既然有现成的列，就不该去依赖这个偏移量。）

## 阶段二才是成败所在

一个数据批次有两个阶段，而提到队首只加速了**阶段一**。

阶段二是**整库**的交付单元循环。按 rollout 六之六记的实测，7997 改细颗粒之后是
**2 890 个生成根**，8 并发约 100 分钟全量收敛。目标 SITE 下的单元可能排在第 2000 位。

**人看到的会是「数据是新的了，但我这个 SITE 的模型还要等一小时」——而他刚按下的那枚
按钮叫「优先更新」。这比不做更难受。** 所以这个功能要么两个阶段都提前，要么改名叫
「优先应用数据」并在界面上说清模型仍需排队。

## Considered Options

- **只提前阶段一**：改动最小，服务端只需给 `execute` 加一个 dbnum 过滤。但按钮名不副实，
  见上一节。
- **两个阶段都提前**（采纳）：阶段一靠收窄扫描范围，阶段二靠给 worklist 一个「优先根」提示。
- **客户端在阶段一完成后对目标 SITE 展开一层、逐个 `/model/ensure`**：服务端今天就支持
  （ADR-0009），只改客户端。但它会与 worker 并发踩踏——`model_update_pending` 行上没有
  claim/lease（rollout 六之六 G5/G6），实测出过孤儿根 `24381/100675`，靠人工重排队列行
  修复。**G5/G6 修好之前这条路不能走。**
- **给队列行加 priority 字段、出队按 (priority, created_at) 排**：最通用。但队列是派生态，
  加一个持久的优先级维度会让「这一行为什么排在这儿」变得说不清——与 ADR-011 §9 拒绝
  「单条取消」同源。

## 十题定案

| # | 题 | 定案 | 出处 |
|---|---|---|---|
| Q1 | 「插队」的语义 | **提到队首**，不打断正在跑的 | ⚠️ 超时自决 |
| Q2 | 扫描范围 | **只扫这一个 dbnum**，`execute` 加 `dbnums` 过滤 | ⚠️ 超时自决 |
| Q3 | 过滤与 MDB 范围的关系 | 过滤是范围内的**子集选择**，请求里的 dbnum 先过 `in_scope`，不在 MDB 声明里的直接拒 | 约束，非决策 |
| Q4 | 单库入口会不会替代全量 | **不替代，两个都留**；按完必须写「其余 N 个库仍有 M 个会话待应用」 | 约束，非决策 |
| Q5 | 阶段二怎么办 | **服务端把 worklist 按「是否在目标 SITE 子树里」排序** | ⚠️ 超时自决 |
| Q6 | 要不要 priority 字段 | **不要**，只做一次性动作 | 代决 |
| Q7 | 界面入口 | 主入口是**模型树 SITE 行右键**，队列面板行内再给一个；**向导里不加** | 代决 |
| Q8 | 要不要确认关 | **要，但是行内轻量确认**。它同样不可取消 | 约束，非决策 |
| Q9 | 改动清单 | 见下节 | |
| Q10 | 排期 | **排在 P0-A + P1 之后** | 见「前提」 |

Q3 那条要说明白：不校验的话就多出一条绕过 MDB 门的路径，而那正是 ADR-0013 花力气统一掉的
东西（三处判定——扫描进不进候选、缺失算不算数、`/dbnums` 的 `excluded`——统一走 `in_scope`）。

Q4 那条与 `CONTEXT.md` 里「排除有两个理由，界面上必须分开数」是同一条精神：不许让人对着
一个收窄的视图以为看到了全部。

Q7 不进向导的理由：那两步是「看清全局再确认」的地方，塞一个收窄入口进去会让它的语义模糊。

## Consequences

**gen-model 先动两项**：

1. `POST /api/v1/update/execute` 加可选 `dbnums: [u32]`，过 `in_scope` 校验后只扫这些库。
   扫描循环本来就是逐库跑的，加一道过滤即可。
2. 阶段二的 worklist 排序接受一个「优先根」提示（随 execute 请求带下来），
   目标 SITE 子树内的交付单元排在前面，其余照旧。

**plant-ui 三项**：

1. `EleTreeNode` 带上 `dbnum`——rs-core 根层查询的 select 列表加一列。
2. 模型树 SITE 行右键菜单 + 一个新 `Cmd`，带 dbnum 与 SITE refno。
3. `model_update_api::execute` 加 `dbnums` 与优先根参数。

**只排一行的副产品**：`POST /queue/promote` 这个接口**可能压根不必要**。只扫一个库就只入
一行，它自然在队列前部；真正的排队只会发生在「已经有别的批次在排」的时候，而那时候
FIFO 本来就该轮到先来的。要不要 promote，等实机验收看到真实的队列长度再定。

**按钮的文案不许含糊**。它做的是「把这一个库的待应用会话应用掉，并优先生成这个 SITE 下的
模型」。不是「只更新这个 SITE」——那句话字面就是错的（事实一）。

## 前提：这个功能建在一片还没验收的地基上

`docs/plans/task-queue-rollout.md` 第十三节记着三件仍然欠着的事：

- **gen-model `master` 现在编译不过**：`batch_worker.rs:267` 调 `record_frozen_end`，
  而实现只存在于未提交的工作树里。换一台机器 clone 下来必定 E0599。
- **实机 curl 验收一直欠着**：8021 上跑的还是旧服务，`/queue` 直接 404。排队 / 合并 /
  冻结三种实况从没在真服务上看过。
- **G5/G6 的跨进程互斥只做了一半**：`model_update_pending` 行上没有 claim/lease。

在这三条之上再开一条新的执行入口，等于在一个没验收过的队列上加一条没验收过的路。
排期照 rollout 自己的那句话走：**哪些事不做，后面所有事都是空转。** 先 P0-A（入库、修编译）、
再 P1（实机验收），然后才是这一条。
