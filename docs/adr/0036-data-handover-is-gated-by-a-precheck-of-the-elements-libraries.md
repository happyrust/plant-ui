# 提资前先查提资元素所在的库，没追平不让提交

状态：**已接受**（2026-11-26。D1、D3、D4 是用户在画板评审里逐条定的；D8 是批准计划时补的；其余随计划批准）。
计划：`docs/plans/2026-11-26-data-publish-precheck-plannotator.md`。画板：`design/三维数据提资.pen`（S15 / S15-A / S15-B / S15-C）。
字段出处：`design/DATA-PUBLISH-FIELD-MAP.md`。术语：`CONTEXT.md`「三维数据提资」。

## 背景

提资会交出旧数据，而且哪里都不报：

- 提资整条路不读水位、不问模型服务。`data_publish.rs` 与 `data_publish_api.rs` 里没有一处看数据新不新。
- 服务供数下模型树读的是文件，rs-server 组包读的是库。所以能选到库里还没有的元素（库没初始化），也能选到库里是旧版本的
  元素（数据水位落后）。前者预览只回「该参考号下没有可发布的节点」，后者交出去的就是旧数据。

要判断的事实服务端已经答得出：`GET /api/v1/node/model-status`（gen-model 接口文档 §4.5.3）对任意节点回答所属的库、
文件最新保存、数据水位、节点的模型判定，只读、按需算；`POST /api/v1/update/execute` 收库号子集，需初始化的库经它做首次导入。

## 决定

### D1　硬拦，不提供绕过

提资前检查没放行，「提交」就灰着。没有「仍然提交」，也没有确认框之后放行。点「提交」时再查一次，这一次仍放行才去查待删除、发提交；
不放行就停下来说一声。

### D2　检查只读，只查提资元素所在的库

逐个提资元素问 `node/model-status`，按所属的库归成行。检查不排任何任务、不改任何数据。别的库落后与这次提资无关，只在脚注里报个数。

数据新不新只认**库的数据水位**，不认节点判定里的「落后」：那一项只看几何变化，改名、改描述不算，而提资交的正是属性。
节点判定只用来回答「模型（连同房间归属）追平没有」。

检查回来的事实是问的那一刻的，会过期。除了元素增删、队列里这几个库的活有变化、更新落定、点「提交」这几个时机，库登记表（随队列一起轮询）
上这几个库的文件最新保存或数据水位动了，本窗也重新问：开着窗等的时候文件又来了新保存，窗口自己变回「不是最新」，不等点「提交」才发现。
登记表只用来发现「该重问了」，判据仍只认检查回来的事实。

### D3　一枚按钮管两类库，增量在前、首次导入在后

「更新到最新」把落后的库排上增量更新、把需初始化的库排上首次导入。需初始化的库在**点这枚按钮时**才排，检查时不排。
顺序靠两次执行请求保证：先发落后的库，回执到了再发需初始化的库；队列先进先出，不改服务端。前一份没发成就不发后一份。

任务落定后本窗重新检查。取回工作不由本窗发：宿主对任何数据批次落定都会自动取回工作，这里不重复。

### D4　放行分两档

- **按库档**（今天的服务端）：库的数据水位追平文件 ∧ 该库没有在排或在跑的任务 ∧ 每个提资元素的节点判定是「最新」或「没有生成单元」。
- **按单元档**（等 gen-model）：该库数据已应用，提资元素所在的交付单元已重新生成（含房间归属）就放行，其余单元后台继续。
  首次导入没有提前放行。

服务端按根回答就绪之前停在按库档，界面写明「这个库的任务跑完才能提交」。房间泳道有待重算时只提醒、不拦：那个数跨库，
饥饿态下会长期不空，并入判据会把无关的提资一直挡住。

### D5　更新不了的，不替人做

下面这些库不进执行名单，行上说出路，或者把它的元素移出本次提资：

- 已阻断（文件异常）。**文件回退不管服务端标没标阻断都算**：人工执行遇到它会清库整库重建（gen-model ADR-021），
  那不是「更新到最新」该替人做的事。
- 够不着、不在本期执行范围。
- 上次更新失败、已停自动重跑。
- 数据水位已是文件最新却缺行（要人发起重新解析）。
- 服务端说这个库此刻排不了（房间参照模型没就绪、增量消费关着）：原话照登，不许诺一次排了也不会跑的更新。
- 数据已是最新、模型没追平、也没有任务在跑：指向模型树右键「重新生成模型」，本窗不替人重算。

文件最新保存里已经没有的元素（被删除）同样挡提交，要移出。

### D6　队列暂停时不替人恢复

队列暂停（自动同步关着）时「更新到最新」灰着，说「队列已暂停：先到任务队列恢复出队」，旁边给「打开任务队列」。恢复会放行队列里
所有库，不该由一次提资顺手做了。身份没对上、服务不消化执行请求时同样灰着并说原因。

### D7　判不了就不拦；没查成要拦

- **判不了**：服务端没有检查接口（老版本），或这一形态不入库（内存 / 读透，数据水位按设计不建立）。检查整块不画，只留一句话，
  提资照旧、不拦。判不了就不装作判过。
- **没查成**：连不上、超时、服务端内部错。既不当成最新也不当成落后，「提交」灰着，主操作是「重新检查」。

两者按服务端给的错误码分，不解析 message。

### D8　这是新入口，旧入口不动

「创建」菜单里加一项「三维数据提资」，打开带提资前检查的新窗。旧的「三维数据接口」——菜单项、窗口、命令、回包——原样保留，照旧不检查。
新窗复用旧入口的表单状态、预览子窗与确认删除子窗，请求与回包另起一组，两边各落各的状态。两扇窗共用那两扇子窗，所以不同时开着：
后开的顶掉先开的；旧窗一次提交在途时新窗不顶它。

## 为什么不是别的做法

- **软拦（提醒之后允许照交）。** 用户在画板评审里选了硬拦。交出去的旧数据收不回来，而不检查的旧入口仍在，确实要照交的人有路可走。
- **检查时发现没初始化就自动初始化。** 首次导入很重、不可取消（gen-model Spec 041 实测一个库 142 – 496 秒），打开一扇窗就起跑不合适；
  改成点「更新到最新」时一并排。
- **按元素判数据新旧。** 要节点级的属性差分，服务端今天的节点判定只看几何。代价见后果 3。
- **暂停时替人恢复队列，或只放行这几个库。** 前者副作用过大；后者要服务端的放行规则（计划阶段四 G5）。
- **直接改旧窗。** 用户明确要求旧入口保持不变。

## 后果

1. 模型服务不在场时，新入口提交不了（没查成 → 拦）。旧入口不受影响。
2. 检查与组包之间仍有窗口：提交时复查之后、rs-server 组包之前又有新保存，交出去的仍可能旧一次。本端做不到原子；
   要关死得 rs-server 在回执里带上组包时的数据水位。
3. 同库别的元素有新保存时，没被改到的提资元素也要等一次增量更新。
4. 从没生成过模型的节点（按需生成的那些）会停在「模型没追平」，要人先在模型树上生成。这是 D4「含房间归属」的直接结果：
   没有模型就没有房间归属。
5. 两个入口并存，词汇上旧窗仍叫「三维数据接口」。收敛与否另议。
6. 按单元放行、优先增量更新、暂停时只放行这几个库、数据水位的时刻，都等 gen-model（计划阶段四 G1 – G5）。在那之前界面按「服务端
   给了才画」做，逐格见字段表。

## 实施约束

1. 判据只在 `crates/plant-ui/src/data_publish_check.rs` 的 `judge_lib` 一处，顺序写死并写进文件头注释；每种行形态、每种判决各有单测。
2. 测试要覆盖：阻断 / 回退 / 够不着 / 已停的库不进执行名单；需初始化排在落后之后；判不了不拦；没查成要拦；提交先复查；
   更新落定后不退回「落后」让按钮再亮一下。
3. 界面上不出现会话号与契约字段名（ADR-0019、DESIGN-SYSTEM 校验清单）；时刻一律是 E3D 写入时刻。
4. 旧入口的测试一条不改、全部照过。
