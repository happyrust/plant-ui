# 供数模式是接入点的一格：整点只认一种、不自动探测、命令面只有服务一条

2026-09-04 起 plant-ui 的读面（模型树 / 属性 / 搜索 / 三维实例 / 工程标识）整条从直连 SurrealDB 换成了
gen-model 的 HTTP 接口（`/tree/*`、`/element/attributes`、`/search`、`/model/records`），底下是 e3d-io 与
e3d-model 直读库文件。原来那条直连库的路（`plant_ui_data::{site_nodes, child_nodes, element_props, …}`）
代码还在，但没人调。用户要两条路都留着、可切。本 ADR 定它们怎么并存。

**供数模式是项目接入点的一格，出厂默认服务供数；库供数是保留档**——给已落盘的 rocksdb 部署、老版本模型服务
与两条路对拍用。新读面只保证服务供数有；库供数缺的那格要标出来（灰掉 + 一句为什么），不许安静空着。

**整个接入点只认一种，不按读面混。** 树走服务、三维走库，看上去是「各取所长」，实际是同一个视口里拼两个时点
的数据（服务读文件最新、库读水位），而且没有任何东西会替它认这件事。ADR-0025 刚刚为模型面挡过「一次装载
混两个源」，这里把同一条纪律放大到整个读面。**房间是唯一例外**：它今天只有库一条，服务供数下经 `/health.mirror`
门控懒连——那不是混，是这一格压根没有第二条路。

**不自动探测。** 客户端不拿 `/health` 的 `data_face` / `mirror` 状态自己决定退回库。自动翻面就是上面那种混源的
无人版：服务端一抖，界面悄悄换了一条路，用户看到的树和三维从此不是一个时点，而日志里什么都没有。要换，人换
（设置窗的下拉框），换的那一刻清场重装（ADR-0021 那条路），三维里不留旧供数方的几何。

**命令面只有服务一条。** 补齐模型（`ensure`，ADR-0009 / ADR-0024）、手动增量更新、任务队列、重新生成、提资、命令
查询在两种供数模式下都走 gen-model HTTP。库供数因此精确地等于「**读面**直连库」，不是「零服务」：没有 `ensure`，
未生成的元素点眼睛就是安静地什么都不画，那是 ADR-0009 之前的坏法。gen-model 不在场时库供数照常出树 / 属性 /
已生成模型，队列面板说「模型服务离线」。

## Considered Options

- **对等双轨**：每个新读面两边都做。代价与读面数成正比，且库那一边的数据面（`pe` / `ATT_*`）在 gen-model
  读透形态下本来就只是写透缓存（gen-model ADR-058 / 09-05 合并计划 N6「库不是内存的镜像」），拿它当一等来源
  是在为缓存做功能。
- **按 `/health` 自动退回**：见上，被否。
- **环境变量当唯一开关**（v0.1.9 HEAD 的 `PLANT_TREE_DATA_MODE`，只管树一条）：开关不进接入点就没人看得见
  它开着；只管一条读面就是按读面混。`PLANT_READ_FACE` 只作开发期压过，在场时下拉框禁用并标注。
- **切模式重启客户端**（照 ADR-0018）：重启是为接入点整体换人；这里接入点没变，只换了一条读路，
  `Reconnect` + 取回工作两条既有路拼起来正是它。

## Consequences

- `plant-ui-app` 多一个 `ReadFace`（enum，两变体）；`data.rs` 的读调用全部经它，源码钉保证不再直接打
  `model_update_api::tree_*` / `plant_ui_data::site_nodes` 之流。数据线程内不许根据错误自行换面。
- `Settings.read_face`（`"service"` / `"store"`，缺省 `service`）住 exe 旁 `settings.ron`，按机器不按项目——它描述
  这台机器能不能碰到库，不是项目的属性。
- 库供数下：库行「模型来源」整格不画（不走 `/model/records` 就没有那一格）；CATA 元素属性给定论；搜索标覆盖面。
- 两条路必须能对拍（`--read-face-parity` 无头子命令）；差异只出报告不判对错。
- 计划见 `docs/plans/2026-09-07-read-face-dual-mode.md`；术语「供数模式 / 服务供数 / 库供数」见 `CONTEXT.md`。
