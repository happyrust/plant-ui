# 子串搜索：本地 ngram 索引跟着输入走，库只出语料

按名称搜索的**子串匹配**（名字中间含某一段）不再打 SurrealDB：plant-ui 自己维护一份
tantivy 索引——收当前 MDB 设计库里**有名字的行**（AMS `/ALL` 实测 91 万行里 143,244
行），ngram(2,3) 分词加小写归一，落盘在可执行文件旁、按（命名空间, MDB）分目录。启动
时打开（实测 2.2ms），之后每次按键都查它（单查含验真几百微秒），ngram 候选再经存储名
`contains` 验真，语义是**真子串**而不是近似（pg_trgm 的玩法）。前缀匹配维持原路不动：
库里 `pe.name` 索引的范围扫、全库范围、毫秒级。于是 ADR-0022 的「前缀搜空了按回车才
搜包含」两段式交互退役：两路并发跟着每一次按键走，下拉里前缀命中在前、子串补充在后。

库内方案是量死的，不是嫌弃出来的。同一个词（`RS-C`，14 条命中）在 91 万行上三种写法：
子查询限库 83.6 秒、单 WHERE 让规划器自己挑 88.9 秒、`WITH NOINDEX` 116.4 秒——
三个数说的是同一件事：**贵的不是索引选择也不是 SQL 形状，是把 11 列文档逐行读出来这
个动作本身**（ADR-0012 当年判 `pe_dbnum_index` 负优化，这回 NOINDEX 反而更慢，索引
无罪）。窄表也验过尸：物化 103.5 秒，建好后库内扫一遍仍要 19.5 秒，连当加载源都不配
——从窄表分页读 47.7 秒，比直接从 `pe` 分库读（31.4 秒）还慢。SurrealDB 自带的全文
索引（`define_fullname_index`，从未启用）用 `class` 分词器按分隔符切词，`RS-C` 这种
跨过 `-` 的针它接不住，而且建在热表 `pe` 上会拖慢 gen-model 的每一次写入。

tantivy 用真语料量过四个数：建索引加落盘 152 毫秒、索引体积 7.4MB（语料 6.1MB）、
重开到能查 2.2 毫秒、单查含验真几百微秒；`rs-c` 的 14 条与库内逐行比对结果一致，
`rs-c1` 的 0 条反查语料证实为真，大小写不敏感成立。换算到将来全库 625 万个有名字的
行：索引几百 MB、建一次几秒、查询仍毫秒级——**全库扩展和候选排序（BM25 就位）这两
条路都留着**，这正是不用「语料平面文件 + memmem 扫」那个更便宜方案的理由。

索引会陈旧，陈旧靠戳管理：每库一条 `(dbnum, 已应用会话号, 行数)`——行数走 dbnum 索
引（91 万行 count 实测 360ms），会话号读 gen-model 的水位表，皆亚秒。索引目录以戳的
散列命名：目录在就直接打开，不在就后台重建（分库拉语料，实测上限 31.4 秒，拉完建索引
毫秒级）。校验时机：启动、取回工作、重连、任务队列里数据批次到终态，外加命令行
`reindex` 手动兜底（够不着的库在别的项目里改了名，戳看不见，这是唯一的门）。重建期间
界面照 CONTEXT 的诚实原则明说「子串索引准备中」，前缀路照常服务。

代价收下的有三笔：全 vendored 离线构建要为 tantivy 一次性收编约 140 个子 crate
（vendor/registry 长大，构建自洽性不变）；浏览器端（wasm）没有这份索引，子串搜索
在那一侧明说不提供；索引与库之间存在以触发点为界的陈旧窗口，靠戳的触发面加手动重建
封顶。这些都比「每次按键等 84 秒」或「窄表两边维护」便宜。
