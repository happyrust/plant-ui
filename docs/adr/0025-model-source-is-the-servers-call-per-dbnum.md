# 模型从哪儿读由服务端按库判决；客户端只消费，一次装载里一个库只认一个源

gen-model 切到 rocksdb + 摄入形态之后，一个设计库有一段「正在初始化」的窗口：基线在写、
或初始化发布 run 还在把模型行落 rocksdb。此前这段时间 plant-ui 对它要么原地等、要么拿到
错误——而模型服务进程内本来就能从库文件把它的模型算出来。gen-model 2026-09-06 计划 §8
（共识 d-29，spec §4.12）把读侧改成**按库选源**：已初始化的库以 rocksdb 为准
（`model-database`），还在初始化的库由 API 从进程内投影供数（`model-memory`），翻面时在
WS `tasks` 主题发 `model_source_changed { dbnum, model_source }`。本 ADR 定 plant-ui 这一半。

**判据只在服务端一处，客户端不自己拼。** `/dbnums` 每行多一格 `model_source`
（`memory` / `database`）与 `model_source_reason`（`initialization_publishing` /
`data_watermark_unestablished` / `read-through`），`/model/ensure` 与 `/model/records` 的回执
同样带它。客户端**只消费**这些格子——不拿 `applied_sesno`、`initialized` 或任务状态自己推
「这个库初始化过没有」。那会把同一条判据复制到第二处；两处一旦不一致，同一个库两页记录
就混了源，而这正是下面要挡的事。老服务端不给这一格、或字面值认不出（将来第三种源）
一律归 `None`：**整格不画、日志不说**，不许猜成「数据库」——那两个字的意思是「重启后还在」，
猜错了人会以为一批只活在内存里的模型已经落库。

**一次装载按 dbnum 分桶，一个桶只认一个源。** `ModelRecordUnion` 按 `/model/records` 回执的
`dbnum` 分桶，桶里第一页认下的 `source` 就是这个桶的源；同一桶再来一页不同源直接报错，
让调用点整趟重来。同一根分页中途换源（第一页内存、第二页 rocksdb）同样报错。跨库各自的源
是常态（一个库已初始化、另一个还在初始化），不算混源。老服务端不给 `dbnum` 时整次装载算
一个桶——这正是此前「不混两个纪元」的口径，只是粒度从整次装载细到了每个库。**这里刻意没有
SurrealDB 回退**：混两版几何拼出来的视口内部不一致，比一次装载失败更坏。

**翻面只改一格，不重载场景。** 收到 `model_source_changed` 只改任务队列里那个库行的
`model_source`，理由一并清掉（事件不带理由，留着旧的「初始化中」就是一句反话，下一拍
`/dbnums` 会把新理由带回来）；手上那份 `/dbnums` 里还没有这个库就提前一拍去取快照。
三维不动：内存投影与刚发布的行是同一版文件算出来的，下一次范围重载自然读到 rocksdb。
日志说一句，人等的多半就是这件事。

**界面上怎么说。** 库行类型旁一个字形（数据库 / 内存），悬停与行内明细里是整句
「模型来源：数据库」「模型来源：内存（初始化中 / 未初始化 / 读透）」；说明列空着时整句
摆进去，装不下就只剩字形。「内存」用提醒色不用危险色——它不是出事，是「这批模型此刻活在
进程里、重启后由初始化发布落库」，值得看见、不值得惊动。装载与按需生成的日志在计数后面
挂半句「其中 dbN 由 API 从内存供数（初始化收口后自动改读 rocksdb，不必重载）」；全部以
rocksdb 为准时什么都不说，那是常态。

**已初始化库的批量读仍经 `/model/records`**（gen-model 计划 Q7 取 (a)）：客户端一条路，
判据只在服务端一处。ws 直连平表快路 `plant_ui_data::model_instances_anc` 保留给测试与
`scope_probe`，主界面不走它。

代价：翻面正好夹在一次装载的两次请求之间时，这一趟以「混源」失败，要重查一次；这是
刻意的，出错的那句话会说清是初始化发布刚翻面、重查即可。
