## 4. 遮罩为什么不开多重采样（DX12 上查到的）

第一版遮罩是「屏幕分辨率、遮罩相机 MSAA 4×」。Vulkan 与 WebGL2 上没有问题，DX12 上（同一块 RX590）画出来是坏的。同一个程序、同一个点连点四次：

| 运行（第一版遮罩） | 每次点选后的描边像素 |
|---|---|
| Vulkan | 2099、2099、2099、2099 |
| DX12 | **0**（+0.5 s / +2 s / +4 s 三张都是 0）、2099、**3161**、**3161** |
| DX12，`PLANT_UI_IDLE_RENDER=0`（不停画） | 四次点选、12 张截图**全是 0** |

2099 是对的数；3161 多出来的一千多个像素是轮廓里面成对的坏点（`dx12-msaa-mask-speckle.png`）。关掉 GPU 间接绘制也一样：头一回是空的，之后带坏点（`zoom-dx12-msaa-mask-speckle.png`）。

排查时只把遮罩相机的多重采样关掉、别的不动：DX12 上六次点选都是 2175，没有坏点。所以问题出在「多重采样的遮罩相机」这一环；是显卡驱动的事，还是 wgpu / Bevy 在 DX12 上处理多重采样离屏目标的事，**没有定位**，也没有在别的显卡上试过。

最终方案不依赖各家驱动的多重采样解析：

- 遮罩相机 `Msaa::Off`，遮罩图按视口屏幕分辨率的 2 倍画（每个屏幕像素 2×2 个遮罩像素）。
- 全屏节点分两段：`selection_mask_resolve.wgsl` 用线性采样把 2×2 的 alpha 平均成一张屏幕分辨率的单通道覆盖率图（`R8Unorm`），抗锯齿出在这一步；`selection_outline.wgsl` 在覆盖率图上找边、叠色。
- 结果见 3.2：Vulkan 与 DX12 都是 2116，第一次选中就有描边，连点不变。

代价是显存（按纹理尺寸算的，没有实测）：有选中件时遮罩相机开着，多占 4 张遮罩大小的纹理（输出图、两张主纹理、深度，各 4 字节一像素）加一张覆盖率图，合每个屏幕像素 65 字节；第一版是 44 字节。本机视口 1477×889 物理像素，遮罩 2954×1778，约 85 MB（第一版约 58 MB）。遮罩的像素数封顶 1600 万（约 256 MB），视口大到 2 倍放不下时等比例缩，最少缩回屏幕分辨率。没有选中件时遮罩相机关着，只剩输出图与覆盖率图（本机约 22 MB）。

**另一件老问题，不在这次范围**：DX12 + PBR 外观下主场景本身画不出来，只有背景与零星坏点。改前的程序（11-05 构建）一样（`dx12-pbr-before-change.png`），改后也一样、但描边是完整的（`dx12-pbr-after-change.png`，描边像素 1471）。试着把 PBR 主相机的多重采样关掉，画面就正常了（`dx12-pbr-main-msaa-off-experiment.png`，描边 1588，连点三次不变）——这个实验没有提交，关掉它 PBR 外观就没有抗锯齿了，要不要处理、怎么处理等用户定（已定：这一轮不动，记为已知问题，理由见计划「进度」的「已定的四项」）。本机缺省后端是 Vulkan，不受影响。

## 5. 没验到的

- **真实大库**：只在演示厂（7 个件）上看过。选中几千上万个件时遮罩相机多画的那一趟要多少时间，没有数据；遮罩现在是 2 倍分辨率，这一趟只会比第一版更重。

- **X-Ray 叠选中**：演示厂开不了房间 X-Ray，只有单测（状态要描边、颜色与 alpha 不变），没有截图。
- **直段截断、孔洞预览下的选中**：只核对了代码路径（见计划「实施」末尾），没有实拍。

## 6. 追加：PBR 外观的悬停预选（同日）

决策见 ADR-0032 修订（2026-11-18）第 8 条，做法见计划「进度」的「追加 PBR 外观的悬停预选」。一句话：PBR 外观下鼠标指着未选中的元素，它换成悬停橙（与 E3D 外观同一个色，沿用自己的透明度，不描边），实体另加一点自发光（`PBR_HOVER_GLOW`，悬停色线性值的 30%）。

- `cargo clippy -p plant-ui -p plant-ui-view3d -p rs-plant --all-targets`：exit 0。告警的行号对过这次改动的行（`look_materials.rs` 90 行、`lib.rs` 72 行）：落在上面的 0 条。
- `cargo check -p plant-ui -p rs-plant --all-targets`、`cargo build -p rs-plant`：exit 0。

### 6.2 怎么拍的

- 场景与启动同 2.1，PBR 外观，缺省配色。桌面是最终代码的 `target/debug/rs-plant.exe`，缺省后端 Vulkan；网页端是最终代码重编的包（放在不入库的 `tmp/`，**没有覆盖 `web/public/pkg`**），无头 Chrome，页面 `?look_demo=1&look=pbr`。
- 指针走的是真实的指针路径（桌面：egui 检视口；网页：无头浏览器的鼠标事件），到位后等 1.5–1.8 秒截图。「指针移开」是把指针挪到视口外。
- **取点**：相机从下往上看，所有件都在房间体里面，所以指得到的只有房间体，和底面贴着房间地板的件（方箱、立柱的底面与地板同在 Z = 0）。取了三个点（截图坐标，两端相同）：立柱底 (988, 468)、方箱底 (740, 420)、房间 (875, 391)。
- **共面处指到谁不稳定**（拾取的老行为，这次没动）：贴着地板的那几个面，射线到「件的底面」与「房间地板」等距，拾到哪个由浮点舍入定。桌面上在方箱底面试了五个点：(740, 420)、(690, 430) 指上去亮的是方箱，(723, 405)、(700, 400)、(760, 440) 亮的是房间体。更早的一次运行里，同一个点 (723, 405) 先后拾取两次：方箱没选中时拾到方箱（日志 `hit=Some((9000000004, Vec3(3.9676366, -1.0967255e-5, 23.287966)))`），方箱选中之后拾到房间体（`9000000007`，命中点 `(3.9676268, -1.9073486e-6, 23.287956)`）——两次命中点都在地板平面上。点选与悬停走的是同一条拾取，同理。上面三个取点是试出来稳定的，网页端同样的点结果相同。
- 像素差是三维视口范围内逐像素比（任一通道不同就算），描边像素的数法同 2.1。桌面截图是 150% 缩放下的逻辑分辨率，网页是 100%，两端的像素数不能直接比。

帧与日志：

- 网页端相邻两帧的最长间隔（毫秒；稳定 60 帧时是 17）：空闲 17、首次指着立柱 17、首次指着方箱 17、首次指着房间体 17、移开 17、再指立柱 17，没有超过 100 ms 的。每两秒一报的平均帧时间 16.6–17.0 ms（页面刚打开时的头两报是 3–6 秒一帧，在指针动之前；加悬停色之前、当天早些时候那几次 PBR 外观的运行也是这样，是启动阶段的事）。
- 浏览器控制台：没有着色器、WebGL、wgpu 的报错；只有静态服务没有后端接口带来的 404（`/api/v1/*`、`/assets/config/e3d.project.ron`）。
- 桌面这次运行的日志里没有 WARN / ERROR。帧时间读数是 32–38 ms：窗口停在屏幕外本来就被限在约 32 ms（见 3.2），当时机器上还有别的编译在跑，这组数看不出有没有变慢。悬停没有新增每帧的工作，只在指的目标变了时给新旧两个目标各换一次材质。
